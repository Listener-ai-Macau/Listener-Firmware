# V2 Status LED Firmware Contract

This firmware pass implements the V2/N16R8 status lighting as a centralized `status_led` component with a separate strip backend. Business code talks to semantic APIs such as `status_led_set_ble_state()` and `status_led_notify_key_event()`; it does not know whether the physical LEDs are WS2812, a future RGB driver, or another strip implementation.

## Hardware Resources

- `LED1`-`LED6`: semantic status rail on `PWM_RGB_Status`, `BOARD_PINS_RGB_STATUS_IO`, GPIO1.
- `LED7`-`LED10`, `LED15`-`LED16`, and `LED23`-`LED28`: EC11 12-LED knob ring on `PWM_RGB_EC11`, `BOARD_PINS_RGB_EC11_IO`, GPIO5.
- `LED11`-`LED14`: local key feedback on `PWM_RGB_KEY`, `BOARD_PINS_RGB_KEY_IO`, GPIO13.
- `LED17`-`LED22`: edge/frame group on `PWM_RGB_Edge`, `BOARD_PINS_RGB_EDGE_IO`, GPIO4.
- `GPIO14` is reserved for `BAT_CHG_IO` in the accepted V2/N16R8 board profile and must not be used for `PWM_RGB_KEY`.
- `VDD_LED` has no firmware-controlled enable pin in the current board contract. Firmware treats the rail as hardware-powered and exposes this as `vdd_led_enable=always_on_assumed` in `~LED:STATUS`.

## Semantic Rail

Default order is fixed until real hardware silkscreen validation proves otherwise:

- `LED1=PWR`
- `LED2=BLE`
- `LED3=REC`
- `LED4=AI`
- `LED5=OK`
- `LED6=WARN`

`PWR` owns battery and external-power state. While unplugged, it uses green for healthy battery, amber for medium/lower battery, steady red for low battery, and red double-flash for critical battery. While USB/VBUS is present, it uses white: a slow always-running breath while plugged in and not confirmed full, then steady white once charge-full has been debounced and latched for that USB session. `BLE` owns pairing, reconnect, connected confidence, and user-requested re-pair confirmation. `REC` only lights for a real capture/upload source named by firmware. If capture is unavailable, firmware shows only `WARN`. `AI` owns the local post-stop transfer/thinking window plus host-confirmed text processing and OTA progress, so it can start immediately after a stop key is accepted. `OK` is a visible 2.0 second success confirmation after the host reports processing done. `WARN` owns retryable and hard errors without borrowing source LEDs or decorative zones.

## BLE Connection Source Of Truth

GAP/HID connection state is the source of truth for the BLE semantic LED. Advertising is allowed to drive `pairing` or `reconnecting` only while the GAP layer has no active connection. If a stale advertising-complete or advertising-restart path fires after the host is already connected, firmware skips advertising and refreshes `connected` instead of allowing `pairing` to overwrite the LED state.

After a connected event, the BLE LED gives a short blue connected-success confirmation on `LED2=BLE`. While the device is still ACTIVE, including quiet-but-not-idle time, ordinary HID-only `connected` stays visible as a low-base blue double-flash heartbeat so the operator can tell the board has not entered idle yet and can also see that Listener-Type has not been confirmed ready. `TYPE_READY` is the Listener-Type-ready active BLE state: after Listener-Type heartbeat/readiness has been observed it uses steady blue and keeps that visual state through short heartbeat misses. The audio transport still uses the strict 12 second heartbeat timeout for send/readiness decisions, but the LED has a 30 second Type-ready hold so routine host scheduling jitter does not look like Type is disconnecting; explicit `TYPE:BYE`/`TYPE:STOP`, notify disable, or BLE disconnect clears the hold immediately. In connected/disconnected low-power idle, the low-power renderer keeps PWR visible and leaves connected/TYPE_READY BLE dark while REC/AI/OK/WARN and decorative zones stay off; routine Listener-Type heartbeat timeout/restore only updates the semantic BLE state and must not reopen an active BLE window. Pairing, reconnect, and user-requested re-pair remain the only low-power idle BLE attention cues. Battery idle keeps a low amber PWR fallback if the live battery sample is temporarily unavailable.

Manual preview and clear commands are not BLE source-of-truth events. If a test preview clears the BLE semantic state while HID remains connected, the next connected HID battery/status update resynchronizes `LED2=BLE` to `connected` or `TYPE_READY` without restarting the connected confidence animation.

Repeated same-state BLE callbacks are idempotent: they do not restart the status window or confidence window. This prevents host subscription noise from making the PWR green status indication look like an irregular post-connect blink.

User-requested re-pairing, including EC11 double-click recovery and `~VREC:RECOVERY`, is a BLE connection flow rather than an error flow. It calls `status_led_notify_ble_repairing()`, clears stale REC/AI/OK state, and gives `LED2=BLE` plus the EC11 ring a bounded blue double-pulse confirmation window even if BLE was already pairing, so an accepted EC11 double-click is visibly acknowledged every time. The edge/frame group stays off during the pairing cue. Hard failures while clearing bonds, rotating identity, or restarting advertising still use `WARN` only.

## Flash Diagnostics

Unplugged/no-serial LED behavior must be reconstructed from flash-backed diagnostics after reconnect, not from live serial output. The status LED component persists `DIAG_LED_POWER_INPUT`, `DIAG_LED_VISUAL_STATE`, `DIAG_LED_OUTPUT_STATE`, and `DIAG_LED_FRAME_RGB` so a post-reconnect dump can show LED-side power/charge/full flags, raw and display-latched battery level, suppressed battery-only display rises, PWR RGB and color class, active PWR/BLE/REC/AI/OK/WARN bits, EC11/edge presence, status color classes, output intensity summaries, and output disable/resume transitions. Raw battery readings remain unchanged for diagnostics and safety; the PWR battery color uses the display-latched level so battery-only voltage rebound cannot flip amber/green.

For the USB-unplug light-cycle issue, a PASS or root-cause claim must cite decoded `summary.param_highlights.status_led.power_input`, `status_led.visual_state`, `status_led.output_state`, optional `status_led.frame_rgb`, `power.external_power`, and `power.sleep_wake` event refs from the unplugged interval. Dump flash diagnostics with `tools/dump_diag_log.ps1`, decode with `tools/decode_diag_log.py`, then validate the decoded bundle with `tools/verify_unplugged_flash_diag_bundle.py --expect-pwr-class amber --expect-pwr-class green` when reproducing the observed yellow/green PWR cycling.

`~LED:STATUS` prints a bounded set of detail lines. Its `detail=power` line reports `external_power_source=usb_det|charger_status|none`. `usb_det` is the normal VBUS divider path; `charger_status` is a visual fallback for boards where `BAT_CHG_IO` proves the charger is active while `USB_DET/GPIO7` reads low. This prevents a plugged board from falling back to battery-only PWR/BLE behavior while charging. Its `detail=rgb`, `detail=rgb_ec11`, `detail=rgb_key`, and `detail=rgb_edge` lines print a current render-sampled RGB frame for all four LED zones so short BLE pulses and effect-only previews can be logged at the moment the status command is handled, not only from a previous refresh cache.

## Status/Key Mapping Calibration

The camera calibration contract for the first product pass is intentionally limited to the ten status/key LEDs:

- `LED1=PWR`, `LED2=BLE`, `LED3=REC`, `LED4=AI`, `LED5=OK`, `LED6=WARN` on the status strip.
- `LED11=KEY1`, `LED12=KEY2`, `LED13=KEY3`, `LED14=KEY4` on the key strip.

The status and key strips keep separate color-order storage in firmware, both defaulting to `GRB` until camera validation proves a different order for either strip. `~LED:STATUS` exposes `mapping_contract`, `status_physical_map`, `key_physical_map`, `separate_status_key_color_order=1`, `status_query_samples_current_render=1`, and power diagnostics including `raw_charging`, `raw_full`, `full_latched`, and `full_candidate_ms` so static and serial checks can reject EC11/edge assumptions and explain charge-state pin jitter before camera capture. The status command is intentionally split into bounded `detail=contract|brightness|strips|state|power|rgb|summary` lines; tools should parse the final `detail=summary` line for semantic state and use the earlier detail lines for diagnostics. `detail=contract` reports `rmt_tx_dma_supported`, `rmt_tx_dma_strategy=status_strip_dma_full_frame_buffer`, `rmt_strip_all_available`, `rmt_tx_dma_all_strips=0`, `low_power_status_tx=non_dma_clear_and_final_frame`, `low_power_final_latch_writes=3`, and per-strip `rmt_tx_dma_requested`, `rmt_tx_dma_actual`, `rmt_tx_dma_fallback`, and `rmt_mem_block_symbols`. On the current ESP32-S3 V2 hardware the active expected pattern is `rmt_tx_dma_requested=status:1,ec11:0,key:0,edge:0`, `rmt_tx_dma_actual=status:1,ec11:0,key:0,edge:0`, and `rmt_mem_block_symbols=status:1024,ec11:48,key:48,edge:48`; after low-power idle sends its non-DMA final latch, a status query may report `status:0` actual until the next active status frame restores DMA. Future DMA changes must update this contract only with physical validation evidence instead of silently changing the current board behavior. `detail=strips` repeats each physical strip with `avail`, `dma_req`, `dma`, and `dma_fb` markers. `detail=summary` reports separate `PWR`/`BLE`/`REC`/`AI`/`OK`/`WARN`/`EC11`/`KEY`/`EDGE` active flags so semantic status, local key feedback, knob accents, and frame accents can be judged independently. Re-pair uses a BLE plus EC11 confirmation cue, so `ble_repair_ms_left` should be nonzero during the bounded user-requested re-pair window and then return to `0` while ordinary `ble=pairing` carries the ongoing semantic state. `detail=state` and `detail=summary` report `shutdown_confirm_active`, `shutdown_confirm_latched`, and `shutdown_confirm_elapsed_ms` so a pending shutdown cue can be verified even if a live power sample updates `last_reason`. `detail=state`, `detail=power`, and `detail=summary` report `preview_ble_override_ms_left` during manual product-scene preview. `detail=state` and `detail=summary` also report `preview_effect_only`, which must be `1` during dedicated LED-effect tuning runs that intentionally suppress PWR/BLE rendering and live power/BLE interference. `detail=brightness` and `detail=summary` also expose `budget_scale_percent` and `budget_limited_by_current` so you can confirm whether a requested 0-100 brightness is being reduced by current limiting. The manual `TEST:PIXEL` path can also address EC11 and edge/frame LEDs for hardware bring-up, while the first camera mapping contract remains limited to status/key.

BLE animation phase is tracked separately from generic visual transitions. `detail=power` reports both `ble_transition_ms` and `last_transition_ms`; `power_change` may refresh the PWR/status window on a plugged board, but pairing/reconnect/re-pair BLE pulses and the edge/frame BLE cues use the BLE phase so charge-state polling cannot restart or hide the connection cue.

Manual `~LED:PREVIEW` scenes temporarily hold their requested BLE state for 15 seconds, so human review popups and their repeated `~LED:STATUS` queries are not overwritten by real connected/reconnect callbacks while the scene is being judged. `clear`, `off`, sleep, error, and real re-pair events clear that preview override.

## Driver Boundary

`status_led.c` owns the business state machine, semantic LED mapping, current budget, USB commands, and frame rendering. `status_led_strip_backend.c` owns physical strip output for all four physical zones: status, EC11 knob, key, and edge/frame. The shared backend owns RGB byte order, ESP-IDF RMT at 10 MHz, per-strip RMT DMA selection, the WS2812 encoder, and a 300 us reset latch with 4020-compatible bit timing. The current V2 hardware keeps advanced status REC/AI effects on the status-only DMA path while EC11, key, and edge/frame stay on ordinary RMT channels. Low-power transition clear and final PWR-only latch frames temporarily use non-DMA status RMT, because live idle validation showed the DMA status path could leave physical LED3-LED6 latched on while firmware rendered only PWR. Future DMA changes stay below the backend boundary and need both physical idle-latch evidence and advanced-effect flicker evidence before being exposed.

The status LED task refreshes every 50 ms while active and sends only strip frames whose RGB data changed, so a stable status rail does not force other zones to retransmit, and EC11/edge accent-only motion does not repeatedly refresh the status rail. When multiple strips do change, the status strip is transmitted last. Recording/processing frames with active `REC`/`AI` and inactive `OK`/`WARN` normally repeat the status-strip packet only when the status RGB data itself changed, using the black tail guard to reinforce LED5/6 at zero. REC+AI overlap is the exception: it may use a very slow 1%-step in-phase LED3/4 brightness change, but it sends each changed status frame only once so the overlap animation does not multiply tail disturbance. BLE pairing/reconnect and connected-confirmation cues are capped near the steady connected blue level rather than using a full-bright blue spike, which keeps the BLE transition visible without lighting the shared status diffuser hard enough to look like all six status LEDs are flashing. The RMT strip backend can use SOC-supported TX DMA when a strip selects it, resets the WS2812 encoder before every transmit and before retrying an invalid-state transmit, appends six extra black guard pixels after the real six status LEDs, and keeps BLE, OTA, keyboard scan, power manager, and diagnostics out of software bit-banging.

Bring-up lesson: WS2812-style LEDs latch the last complete color frame, but the data line still needs a defined idle level after the frame is sent. On the V2 status rail, live evidence showed the DMA status path could corrupt the tail of an otherwise PWR-only idle frame, leaving physical LED3-LED6 on while `detail=rgb` reported them off. Active BLE/recording/processing frames keep the status DMA channel enabled between changed frames so `.eot_level = 0` holds the line low without repeated enable/disable edges. Low-power stable idle first sends a non-DMA zero clear frame, keeps the transport alive through the 80 ms clear-to-final gap, then sends the non-DMA restrained PWR-only status frame three times before releasing all four RMT transports and driving each data GPIO low. The LEDs keep the final PWR-only latch while firmware avoids low-power DMA retransmits or enabled idle windows that can corrupt the status rail into an all-on state. Full sleep/manual all-off still suspends all strips after transmitting black. Do not switch the status data pin to ordinary GPIO between normal active frames, and do not disable RMT after every successful dynamic frame; either pattern can create WS2812-visible pulses and flash LED3-LED6. Preview state changes schedule repeated zero status frames when leaving non-idle accents or BLE attention states, so stale LED3-LED6 data is cleared before the next effect. The 2026-06-23 active-DMA/idle-non-DMA decision and evidence are recorded in [status_led_active_dma_idle_nondma_stability_20260623.md](../validation/status_led_active_dma_idle_nondma_stability_20260623.md). If `~LED:STATUS detail=rgb` reports only PWR/BLE active while LED3-LED6 physically flash during an idle transition, check RMT idle-drive behavior and the status DMA policy before changing semantic rendering.

AI change guardrail: do not "fix" idle all-on by globally disabling status-strip DMA or by routing ordinary active transition clear frames through the non-DMA path. The only status frames allowed to force non-DMA are frames sent while `low_power_active` is true or while the final hardware-shutdown PWR-only confirmation is active, covering the low-power clear/final PWR-only latch before transport suspend and the last shutdown latch. Do not suspend the RMT transports after the low-power clear frame; suspend only after the repeated final PWR-only latch. Normal active preview/effect switching, including clear frames used between REC/AI/OK/WARN previews, must stay on status DMA from the first active frame. The bad pattern `force_clear_tx || low_power_active` caused status RMT reconfiguration plus `flush timeout` during preview switching; the intended code shape is `status_force_non_dma = pwr_only_final_latch`, where that latch is only `low_power_active || shutdown_final_active`.

Shutdown final contract: `~LED:STATUS detail=contract` reports `shutdown_final_status_tx=non_dma_pwr_only_latch`. Final hardware-shutdown confirmation clears every non-PWR LED and sends the restrained PWR-only status latch through the same non-DMA repeated-write path as low-power idle, while ordinary active REC/AI/effect switching remains on status-strip DMA.

## Source Of Truth

Code constants and `~LED:STATUS detail=contract` are the source of truth for exact status LED effect parameters. This document records operator semantics, command entry points, and validation evidence routing; do not recover brightness ranges, timing, DMA policy, or retry behavior from prose. When a behavior must be enforced, put it in firmware, a machine-readable contract field, or a static validation check.

## Profiles And Budget

Profiles are persisted in NVS through `~LED:PROFILE <off|low|standard|ambient|factory>`. A separate user brightness cap is persisted through `~LED:BRIGHTNESS <0-100>` and applies as the hard routine-product brightness limit across the status, key, EC11, and edge zones. `~LED:BRIGHTNESS` remains a compatibility command and writes both device brightness profiles. New desktop/device settings should prefer `~DEVICE:SETTINGS` plus `~DEVICE:SET plugged_brightness=<0-100> battery_brightness=<0-100>` so plugged and battery operation can have different global caps, and `~DEVICE:SET led_status=<0-100> led_key=<0-100> led_ec11=<0-100> led_edge=<0-100>` when each physical LED zone needs its own maximum. Fresh devices default to plugged brightness 80%, battery brightness 50%, and 100% per-zone caps; animations may breathe below those caps but must not replace them with fixed hidden maxima.

User brightness scales the whole routine effect envelope before the profile cap is applied. A 50% user brightness setting scales the external-power breath's low and high points together, rather than clipping all samples above 50% into a flat line. The charging breath is intentionally shallow and slow so plugged-in charging reads as alive without pulling attention like a warning or recording state.

In firmware, `plugged_brightness` and `battery_brightness` are now applied as physical duty percentages (0-100% directly maps to the internal 0-255 output scale), which makes the numeric setting more predictable when you are tuning actual lamp intensity.

- `standard` is the product default. It does not add a hidden percent cap above the user plugged/battery brightness setting.
- `low` keeps low-power visual behavior and a smaller current budget, but the visible percent cap still comes from the user brightness setting.
- `ambient` permits restrained idle accent behavior when the EC11 and edge chains are available, without adding a hidden percent cap above the user brightness setting.
- `off` turns routine non-safety output off; safety/error/test paths can still light.
- `factory` keeps the full 100% profile path for calibration, manufacturing, and hardware bring-up; routine product effects still respect the user brightness cap unless they are explicit safety/error/test output.

Current is still estimated per frame with 20 mA per RGB channel at full scale. `standard`, `low`, and `ambient` have product budgets so broad multi-LED effects are dimmed by current budget when needed; those budgets are not a second fixed percent cap. Explicit safety/error/test paths retain the full bring-up budget. The renderer suppresses repeated RMT writes for unchanged frames and slows the task cadence in static idle states; state changes notify the task so button, recording, processing, and test feedback still appear promptly.

## Product Effect Language

- Active connected state is readable but not dominant: ordinary HID-only `connected` keeps `LED2=BLE` visible as a low-base blue double-flash heartbeat until `power_manager` enters idle, while `TYPE_READY` is steady blue so Listener-Type readiness is distinguishable from plain BLE without leaving the BLE color family. When `power_manager` enters connected or disconnected idle, routine active-work LEDs are cleared, connected/TYPE_READY BLE turns off, and only the restrained PWR indicator remains visible; pairing, reconnect, and user-requested re-pair can still blink BLE as attention states. REC/AI/OK/WARN, key, EC11, and edge/frame stay off until a real key/recording/processing/LED command resumes normal feedback. Low-power idle uses 12% for single-channel PWR colors and 4% per RGB channel for white PWR so white has the same approximate total drive as green/orange. Low-power idle sends the final PWR-only status frame before immediately suspending the LED transports, so quiet idle does not keep retransmitting BLE or status frames.
- External power overrides battery-color display on `PWR`: USB plugged and not confirmed full is a continuous slow white breath with an 8%-38% product range while idle, so the difference between the low and high points is visible without feeling like a warning, recording state, or high-energy animation. During recording or processing, `PWR` holds a steady readable 28% white floor so it does not add another dynamic status-rail source. Charge-full requires USB present, an active charge-full pin, no active charging pin, and a near-full battery reading for the debounce window; after that it latches for the current USB session and shows steady white until USB is unplugged.
- The external-power white breath, full-charge steady white, BLE, REC, AI, OK, key feedback, EC11 accents, and edge/frame accents are routine product output and obey the active plugged/battery user brightness cap plus the matching per-zone maximum cap. Their animation curves may use lower intermediate levels, but their routine maximum is clipped by explicit user settings rather than a hidden profile constant.
- Pairing and reconnect use recognizable blue pulses without turning the whole status rail into an animation surface. Pairing and reconnect use only the `BLE` semantic LED, with the EC11 ring and edge/frame group off unless the user is actively pressing or rotating EC11. User-requested re-pair/reset uses `BLE` plus a low blue EC11 full-ring double-pulse confirmation, while the edge/frame group stays off. A successful connected transition gets a short BLE-only blue confirmation. Re-pair must not light `LED6=WARN` unless the recovery operation actually fails.
- Recording uses `rec_level` only for status `LED3=REC`; it does not borrow key LEDs and does not clear independent `PWR`/`BLE` status. Firmware exposes `rec_level` in `~LED:STATUS` and accepts `~LED:REC_LEVEL <0-100> [hold_ms]` for repeatable review. The visual envelope is smoothed, rate-limited, and quantized before rendering. EC11, key, and edge/frame do not follow PCM brightness; they keep their own low-load product accents. During active recording/processing, `PWR` and connected `BLE` stay readable even after the ordinary status window expires. Starting a new recording clears stale `OK` and retryable recording warning state so `LED5=OK`/`LED6=WARN` cannot linger into active capture.
- Processing uses status `LED4=AI` immediately after firmware accepts a recording stop and when the desktop host starts streaming/ASR processing. The status `AI` LED stays purple and uses a brightness-only grouped da-dada thinking beat rather than a plain breath; the exact scan parameters live in the code constants and `~LED:STATUS detail=contract`, not in this prose. When recording and processing overlap, status `REC` follows the bounded audio envelope while status `AI` keeps the thinking cue; both stay on the dedicated status strip and overlap frames still use only one status-strip write. EC11 and edge/frame give priority to the stable low warm-gold recording cue instead of same-zone gold/purple mixing, and AI remains visible on status `LED4`. `LED1=PWR` and `LED2=BLE` keep their own state unless power/BLE state actually changes. Starting a new processing window clears stale `OK` and retryable AI/OTA warning windows before the first processing frame.
- Firmware recording transfer starts `AI` locally as soon as stop is accepted, so releasing the stop key has immediate thinking feedback while the final audio tail is delivered. The desktop host can refresh processing with `VREC:PROCESSING:START`, clear it with `VREC:PROCESSING:STOP`, and report completion with `VREC:PROCESSING:DONE`; `DONE` turns `AI` off and flashes green `OK` for a 2.0 second visible confirmation window.
- Key LEDs remain local transient feedback only: detected press and release-tail feedback use white so every physical press is visibly acknowledged. KEY1-KEY4 intentionally use active-low light-sleep wake plus 20 ms scan and 20 ms debounce for press/hold detection, not runtime GPIO interrupts; restoring a runtime key GPIO ISR can create interrupt storms and reset the board during press/hold. Confirmed gesture feedback uses a bright purple with distinct timing: single click is one visible flash, double click is two visible flashes, and long press stays solid purple while the key remains held. The KEY1-KEY4 double-click window is intentionally short at 200 ms so a single click feels responsive; two deliberate fast taps are still treated as a double click. Starting any purple gesture confirmation clears the same key's white release tail, so the purple pattern must not end with a white flash. Once the visible purple flash pattern is complete the key LED must be released so a following physical press can show white immediately instead of being swallowed by a stale black feedback tail. Long press release refreshes the purple long confirmation for 1000 ms, matching the 1000 ms white-to-purple hold threshold, and it must not fall back to a white release tail after a held gesture. In low-power idle, the first raw press edge also uses the white press cue so short taps prove they were detected even if the key is released before debounce completes; the later confirmed gesture remains purple. Recording and processing no longer light the key strip, so keys do not compete with status semantics or the knob/frame accents.
- EC11 knob and edge/frame LEDs are independent accent surfaces. Standard profile uses restrained accents for recording-only, processing-only, OK, re-pair, and physical EC11 input feedback. Ordinary BLE pairing/reconnect states stay on the `BLE` semantic LED rather than using EC11 or edge/frame cues; accepted user-requested re-pair uses a low blue EC11 full-ring double-pulse synchronized to `LED2=BLE`. EC11 press/hold keeps refreshing the white press cue every 300 ms until the 0.8 second long-press shutdown confirmation starts, so the hold does not go dark before the amber pending-shutdown cue. The EC11 push GPIO uses active-low light-sleep wake plus a bounded 20 ms scan for active and low-power waits, not a runtime GPIO ISR; runtime EC11 push interrupts can storm while flash/cache is disabled and trigger interrupt-WDT resets. EC11 A/B rotation keeps active edge IRQs and a 20 ms low-power backup poll; in low-power idle, any valid rotation edge resumes LED output and refreshes the white rotation cue, while each completed detent still dispatches the configured HID consumer action. Continuous rotation is direction-driven and fixed-step rendered: partial encoder edges refresh the current white head and update direction from the accumulated detent direction, so a single opposite contact-bounce edge cannot flip the cue; each accepted detent seeds the current head and extends the hold window, and the renderer then advances the white head at `STATUS_LED_EC11_ROTATION_STEP_MS` with a directional trailing arc. This keeps the cue visibly moving during a continuous turn instead of restarting at the first LED or going dark between detents, and reversing direction preserves the current head while flipping the trail immediately after the accumulated direction really changes. Avoid restoring detent-only, symmetric-tail, per-edge restart, or raw single-edge direction behavior; those regress the observed knob feel. The input path compresses duplicate raw ISR states, remembers the latest overflow state, and rereads physical A/B after draining a burst; HID consumer backpressure during fast rotation is log-only and must not light `LED6=WARN` because the local EC11 cue already acknowledged the action. If a very light tap produces the raw white press cue but releases before the 30 ms stable-press threshold, stable idle still accepts it as a raw-only short click so users do not need to press many times before one click counts. Debounce, the 200 ms pending single-click/custom-key response window, the 650 ms recovery double-click window, and the 0.8 second long-press threshold use real FreeRTOS elapsed ticks rather than poll-loop counts, because wake/poll churn must not make a short click look like a hold or expire either click window early. EC11 double-click recovery is not a key-style purple gesture: after the second click is accepted within the recovery window, recovery uses the ordinary BLE pairing cue on `LED2=BLE` plus the EC11 blue full-ring double-pulse while edge/frame stays off. Ambient adds calm low-blue idle accents. `rec_level` drives only status `LED3=REC`; processing-only uses matched low violet clockwise motion on EC11 and edge/frame; REC+AI overlap gives recording warm gold priority with the same low-load EC11/edge flow instead of same-zone gold/purple mixing. EC11 short press and rotation add a brief white local confirmation even when pairing or not connected; HID delivery is best effort and must not swallow the local light effect. These accents never set status semantics and are suppressed below low battery except safety/error/test paths.
- EC11 fast-rotation diagnostics are intentionally bounded: rotation feedback may write a flash-backed status diagnostic at most once per 500 ms, and the BLE HID usage queue must remain deep enough for short rotation bursts. High-rate diagnostic writes or shallow HID queues are regressions because they can make the local ring cue fade out while the user is still turning.
- EC11 rotation uses a longer low-tail hold than a press cue: accepted rotation input refreshes the visible floor, the renderer advances the head at the fixed rotation step while the hold remains active, and the rendered ring remains alive through short slow-turn gaps before fading out. Interactive wake from low-power idle cancels the pending all-black transition-clear frame and renders the EC11/key feedback frame immediately, while the low-power entry final clear/PWR-only latch remains intact. Removing this rotation hold, using the shorter press fade, or inserting a black transition-clear frame on interactive wake can make the ring and status LEDs go black mid-turn and then restart on the next detent.
- Status-tail anti-flicker contract: every normal rendered frame clears `LED5=OK` and `LED6=WARN` unless an actual success or active error window owns them. The backend appends six black guard pixels, suppresses unchanged strip retransmits, writes the status strip last, and keeps the data line driven low between active changed frames without switching the GPIO mux or disabling RMT on every frame. Low-power stable idle sends a non-DMA final clear/PWR-only sequence, keeps the transport alive between clear and final latch, then immediately suspends status, EC11, key, and edge transports with all data GPIOs driven low after the repeated final latch. `~LED:STATUS detail=contract` reports `rmt_tx_dma_strategy=status_strip_dma_full_frame_buffer`, `rmt_tx_dma_all_strips=0`, `low_power_status_tx=non_dma_clear_and_final_frame`, `low_power_final_latch_writes=3`, `rmt_idle_drive=active_status_dma_low_power_non_dma_final_frame_then_immediate_all_quiet_suspend`, `low_power_transport_suspend_ms=0`, `status_tail_reinforce=recording_processing`, `status_tail_reinforce_writes=3`, `status_tail_overlap_reinforce_writes=1`, `status_tail_overlap_style=dma_audio_rec_ai_da_dada`, `recording_level_reactive=1`, `processing_thinking_style=single_then_double_beat`, `processing_thinking_color=purple_static`, `processing_thinking_scan_profile=da_long_gap_grouped_dada_rest`, `active_work_status_overlap_dynamic_1pct_eased=0`, `active_work_status_audio_reactive_rec=1`, `active_work_status_thinking_ai=1`, `strip_dirty_tx=1`, `status_tx_last=1`, and `dynamic_active_accents=1`. Historical brightness/cadence trials belong in validation artifacts, not this feature prose. If `detail=rgb` shows only `BLE`/`PWR` active while a camera or eye sees other status windows flash during BLE-only pulses, first check the RMT idle-drive/data-line behavior, then optical bleed, physical signal integrity, or mapping evidence before changing semantic rendering.
- Long-press shutdown confirmation: when EC11 long press crosses the power-control threshold, firmware shows a warm amber pending cue by restoring LED output, holding `PWR` amber, and filling the EC11 ring clockwise over 1.8 seconds; the edge/frame group stays off for this confirmation. After one full ring, the pending cue stays latched at full ring instead of timing itself out; only final long-press hardware shutdown, sleep, clear, or another explicit state transition turns it off. When hardware shutdown is actually confirmed, firmware shows a 1.2 second bright amber `PWR`-only cue before entering sleep so automatic shutdown cannot look like every LED turned on. The confirmation cue temporarily takes priority over REC/AI decorative accents, while `PWR`/`BLE` state remains independently rendered before the final cue.
- Warnings use `LED6=WARN` only. Retryable and hard error pulses do not borrow source LEDs, keys, EC11, or edge/frame accents, so an error is visually distinct from recording, processing, OK, and charging. Health-monitor BLE instability alerts are log-only and must not light `BLE` or `WARN` during idle; hard BLE failures and explicit BLE operation failures can still use the error path. Critical battery remains a dedicated `PWR` safety cue.
- The product palette favors clear semantic colors on the current diffuser: green for battery-good/OK, white for external power and detected physical key/EC11 press feedback, blue for BLE pairing/reconnect/re-pair, gold for recording, red for hard warning, amber for lower battery or retryable warning, and purple for AI plus confirmed single/double/long key gestures.
- RGBW, map, chase, and pixel test commands remain calibration tools and can drive full brightness independent of the product profile.

- `~LED:PREVIEW pairing`, `~LED:PREVIEW reconnect`, and `~LED:PREVIEW repairing` exercise the BLE connection states used for first pairing, host reconnect, and EC11 double-click re-pair recovery. Pairing keeps EC11 and edge/frame off, with `LED2=BLE` carrying the pairing cue. Reconnect keeps a low blue BLE floor with a brighter double-pulse. `repairing` should briefly report `ble_repair_ms_left>0`, keep `WARN` off unless a separate hard failure is injected, use BLE plus an EC11 blue full-ring double-pulse for user-requested re-pair confirmation, and keep edge/frame off.
- `~LED:PREVIEW recording_active` and `~LED:PREVIEW capture_active` are aliases for active device-mic capture, not effect-only previews: they must establish the connected ready baseline first, then add `LED3=REC` while keeping `LED1=PWR` and `LED2=BLE` independent.
- `~LED:PREVIEW recording_processing` shows the connected ready baseline plus active capture and host-processing: `LED1=PWR` and `LED2=BLE` remain independent, `LED3=REC` and `LED4=AI` are added, EC11/edge show low deterministic warm-gold same-cycle flow accents, key LEDs stay off unless physically pressed, and `LED5=OK`/`LED6=WARN` must remain off unless a later success or fresh error command is sent. Run `~LED:STATUS` during this preview and inspect the `detail=rgb` line to verify the current render-sampled status frame, not just a camera frame.
- `~LED:PREVIEW recording_processing_status_only` uses the same status `PWR/BLE/REC/AI` semantics while suppressing key, EC11, and edge accents. Use it only as a diagnostic split: if status-only still flashes physical LED5/LED6 while `detail=rgb` reports `OK=0,0,0;WARN=0,0,0`, the remaining issue is on the status rail itself rather than multi-zone accent interference.
- Dedicated LED-effect tuning must use `~LED:PREVIEW capture_led_only`, `~LED:PREVIEW recording_processing_led_only`, `~LED:PREVIEW recording_processing_status_led_only`, `~LED:PREVIEW processing_led_only`, or `~LED:PREVIEW processing_status_led_only`. These modes run the same product renderer but set `preview_effect_only=1`, keep PWR/BLE and physical key-press feedback out of the rendered frame, clear stale OK/WARN/error windows, and ignore live charge/BLE/key events for visual judgment. Full effect-only modes judge status, EC11, and edge together while the key strip stays off; status-only effect modes set `preview_suppress_accents=1` and keep key/EC11/edge off. Mutating `~LED:*` commands count as USB LED activity, and effect-only preview holds the USB-command power-manager blocker until `~LED:PREVIEW clear` or `~LED:OFF`, so low-power idle cannot clear the review state or hardware-shutdown the board while the human prompt is open. Power samples may still update diagnostic readback, but they do not reset the effect phase or change `last_reason` during effect-only review. Use ordinary `capture`, `recording_processing`, and `processing` only for product-scene review where PWR/BLE participation is intentional.
- `~LED:PREVIEW recording_processing_status_key_stress` is a diagnostic-only repro pattern. It sets `preview_effect_only=1`, drives status `LED3=REC`/`LED4=AI` dynamically while keeping software `LED5=OK`/`LED6=WARN` at zero, and mirrors the status dynamics on the key strip without involving EC11 or edge LEDs. Use the narrower `~LED:PREVIEW status_key_stress3`, `~LED:PREVIEW status_key_stress4`, and `~LED:PREVIEW status_key_stress34` forms for human diagnosis: LED3+KEY1 isolates possible LED5 follow, LED4+KEY2 isolates possible LED6 follow, and LED3/4+KEY1/2 checks the two-channel threshold before the all-key stress.
- `~LED:PREVIEW shutdown_confirm` and `~LED:PREVIEW shutdown_final` exercise the pending and final long-press shutdown confirmation effects without requiring an actual power-off. For pending shutdown review, wait longer than 1.8 seconds and confirm the EC11 ring remains fully lit until `shutdown_final`, `sleep`, `clear`, or a real power-off path clears it. For final shutdown review, confirm `PWR` is the only active LED and the EC11 ring is off.
- Runtime EC11 long-press pending shutdown feedback is canceled on EC11 release unless the power manager has already escalated to the final hardware-shutdown confirmation.
- `~LED:ERROR <ble|recording|ai|ota|power|system> <retryable|hard>`
- `~LED:PROFILE <off|low|standard|ambient|factory>`
- `~LED:OFF` clears test/status output immediately and stays dark until the next status/key event. It is not the sleep path; `status_led_prepare_sleep()` remains the sleep-only full output disable.
- `~LED:WAKE`

When camera capture is not trustworthy, `tools/status_led_manual_calibration.ps1` drives one status/key LED RGBW/off command at a time at 100% brightness and records human-eye feedback under the step validation directory. For EC11/edge bring-up, use direct serial `~LED:TEST:PIXEL ec11 LED7 white 100`, `~LED:TEST:PIXEL edge LED17 white 100`, or full-strip `~LED:TEST:RGBW ec11 edge`/`~LED:CHASE ec11,edge`.

Real V2 hardware validation still has to record the actual RGB color order and physical LED order with photos or video. The firmware default color order is `GRB` for all four strips. Status/key use the 3528 WS2812-style part, while EC11/edge use the 4020 WS2812B part; both datasheets use 24-bit GRB data, but the 4020 part needs the longer reset latch and stricter low-time timing used by the backend.

During 2026-06-08 hardware bring-up, status/key LEDs responded on the current board but EC11/edge LEDs did not light after the firmware was flashed with the 4020-compatible timing above. Treat EC11/edge darkness as a separate hardware pinout or continuity investigation before changing firmware color order or WS2812 timing again.
