# V2 Status LED Firmware Contract

This firmware pass implements the V2/N16R8 status lighting as a centralized `status_led` component with a separate strip backend. Business code talks to semantic APIs such as `status_led_set_ble_state()` and `status_led_notify_key_event()`; it does not know whether the physical LEDs are WS2812, a future RGB driver, or another strip implementation.

## Hardware Resources

- `LED1`-`LED6`: semantic status rail on `PWM_RGB_Status`, `BOARD_PINS_RGB_STATUS_IO`, GPIO1.
- `LED7`-`LED10`, `LED15`-`LED16`, and `LED23`-`LED28`: EC11 12-LED knob ring on `PWM_RGB_EC11`, `BOARD_PINS_RGB_EC11_IO`, GPIO5.
- `LED11`-`LED14`: local key feedback on `PWM_RGB_KEY`, `BOARD_PINS_RGB_KEY_IO`, GPIO13.
- `LED17`-`LED22`: edge/frame group on `PWM_RGB_Edge`, `BOARD_PINS_RGB_EDGE_IO`, GPIO4.
- `GPIO14` is reserved for `BAT_CHG_IO` in the accepted V2/N16R8 board profile and must not be used for `PWM_RGB_KEY`.
- `VDD_LED` has no firmware-controlled enable pin in the current board contract. Firmware treats the rail as hardware-powered and exposes this as `vdd_led_enable=always_on_assumed` in `~LED:STATUS`.

## Semantic Rail

Default order is fixed until real hardware silkscreen validation proves otherwise:

- `LED1=PWR`
- `LED2=BLE`
- `LED3=REC`
- `LED4=AI`
- `LED5=OK`
- `LED6=WARN`

`PWR` owns battery and external-power state. While unplugged, it uses green for healthy battery, amber for medium/lower battery, steady red for low battery, and red double-flash for critical battery. While USB/VBUS is present, it uses white: a slow always-running breath while plugged in and not confirmed full, then steady white once charge-full has been debounced and latched for that USB session. `BLE` owns pairing, reconnect, connected confidence, and user-requested re-pair confirmation. `REC` only lights for a real capture/upload source named by firmware. If capture is unavailable, firmware shows only `WARN`. `AI` owns host-confirmed text processing, thinking, and OTA progress; audio transfer completion alone does not animate `AI`. `OK` is a visible 2.0 second success confirmation after local recording stop/session completion and after the host reports processing done. `WARN` owns retryable and hard errors without borrowing source LEDs or decorative zones.

## BLE Connection Source Of Truth

GAP/HID connection state is the source of truth for the BLE semantic LED. Advertising is allowed to drive `pairing` or `reconnecting` only while the GAP layer has no active connection. If a stale advertising-complete or advertising-restart path fires after the host is already connected, firmware skips advertising and refreshes `connected` instead of allowing `pairing` to overwrite the LED state.

After a connected event, the BLE LED gives a short blue connected-success confirmation on `LED2=BLE`, then uses the 6 second status window plus the bounded 8 second confidence window, with the first out-of-box connection allowed a longer bounded confidence window. Once those windows expire, plugged/external-power standard-profile devices show steady low blue on `LED2=BLE`. On battery, once confidence/status windows expire, connected BLE falls back to a sparse low-blue heartbeat and `PWR` turns off unless the battery is low enough to require a warning.

Repeated same-state BLE callbacks are idempotent: they do not restart the status window or confidence window. This prevents host subscription noise from making the PWR green status indication look like an irregular post-connect blink.

User-requested re-pairing, including EC11 double-click recovery and `~VREC:RECOVERY`, is a BLE connection flow rather than an error flow. It calls `status_led_notify_ble_repairing()`, clears stale REC/AI/OK state, shows a bounded blue BLE double-pulse on `LED2=BLE`, adds a low blue EC11 ring orbit as the user-action confirmation, keeps the edge/frame off, then falls back to ordinary pairing. Hard failures while clearing bonds, rotating identity, or restarting advertising still use `WARN` only.

## Flash Diagnostics

Unplugged/no-serial LED behavior must be reconstructed from flash-backed diagnostics after reconnect, not from live serial output. The status LED component persists `DIAG_LED_POWER_INPUT`, `DIAG_LED_VISUAL_STATE`, `DIAG_LED_OUTPUT_STATE`, and `DIAG_LED_FRAME_RGB` so a post-reconnect dump can show LED-side power/charge/full flags, raw and display-latched battery level, suppressed battery-only display rises, PWR RGB and color class, active PWR/BLE/REC/AI/OK/WARN bits, EC11/edge presence, status color classes, output intensity summaries, and output disable/resume transitions. Raw battery readings remain unchanged for diagnostics and safety; the PWR battery color uses the display-latched level so battery-only voltage rebound cannot flip amber/green.

For the USB-unplug light-cycle issue, a PASS or root-cause claim must cite decoded `summary.param_highlights.status_led.power_input`, `status_led.visual_state`, `status_led.output_state`, optional `status_led.frame_rgb`, `power.external_power`, and `power.sleep_wake` event refs from the unplugged interval. Dump flash diagnostics with `tools/dump_diag_log.ps1`, decode with `tools/decode_diag_log.py`, then validate the decoded bundle with `tools/verify_unplugged_flash_diag_bundle.py --expect-pwr-class amber --expect-pwr-class green` when reproducing the observed yellow/green PWR cycling.

`~LED:STATUS` prints a bounded set of detail lines. Its `detail=power` line reports `external_power_source=usb_det|charger_status|none`. `usb_det` is the normal VBUS divider path; `charger_status` is a visual fallback for boards where `BAT_CHG_IO` proves the charger is active while `USB_DET/GPIO7` reads low. This prevents a plugged board from falling back to battery-only PWR/BLE behavior while charging. Its `detail=rgb`, `detail=rgb_ec11`, `detail=rgb_key`, and `detail=rgb_edge` lines print a current render-sampled RGB frame for all four LED zones so short BLE pulses and effect-only previews can be logged at the moment the status command is handled, not only from a previous refresh cache.

## Status/Key Mapping Calibration

The camera calibration contract for the first product pass is intentionally limited to the ten status/key LEDs:

- `LED1=PWR`, `LED2=BLE`, `LED3=REC`, `LED4=AI`, `LED5=OK`, `LED6=WARN` on the status strip.
- `LED11=KEY1`, `LED12=KEY2`, `LED13=KEY3`, `LED14=KEY4` on the key strip.

The status and key strips keep separate color-order storage in firmware, both defaulting to `GRB` until camera validation proves a different order for either strip. `~LED:STATUS` exposes `mapping_contract`, `status_physical_map`, `key_physical_map`, `separate_status_key_color_order=1`, `status_query_samples_current_render=1`, and power diagnostics including `raw_charging`, `raw_full`, `full_latched`, and `full_candidate_ms` so static and serial checks can reject EC11/edge assumptions and explain charge-state pin jitter before camera capture. The status command is intentionally split into bounded `detail=contract|brightness|strips|state|power|rgb|summary` lines; tools should parse the final `detail=summary` line for semantic state and use the earlier detail lines for diagnostics. `detail=summary` reports separate `PWR`/`BLE`/`REC`/`AI`/`OK`/`WARN`/`EC11`/`KEY`/`EDGE` active flags so semantic status, local key feedback, knob accents, and frame accents can be judged independently. `detail=state`, `detail=power`, and `detail=summary` report `ble_repair_ms_left` during the bounded re-pair confirmation cue. `detail=state` and `detail=summary` report `shutdown_confirm_active`, `shutdown_confirm_latched`, and `shutdown_confirm_elapsed_ms` so a pending shutdown cue can be verified even if a live power sample updates `last_reason`. `detail=state`, `detail=power`, and `detail=summary` report `preview_ble_override_ms_left` during manual product-scene preview. `detail=state` and `detail=summary` also report `preview_effect_only`, which must be `1` during dedicated LED-effect tuning runs that intentionally suppress PWR/BLE rendering and live power/BLE interference. `detail=brightness` and `detail=summary` also expose `budget_scale_percent` and `budget_limited_by_current` so you can confirm whether a requested 0-100 brightness is being reduced by current limiting. The manual `TEST:PIXEL` path can also address EC11 and edge/frame LEDs for hardware bring-up, while the first camera mapping contract remains limited to status/key.

BLE animation phase is tracked separately from generic visual transitions. `detail=power` reports both `ble_transition_ms` and `last_transition_ms`; `power_change` may refresh the PWR/status window on a plugged board, but pairing/reconnect/re-pair BLE pulses and the edge/frame BLE cues use the BLE phase so charge-state polling cannot restart or hide the connection cue.

Manual `~LED:PREVIEW` scenes temporarily hold their requested BLE state for 15 seconds, so human review popups and their repeated `~LED:STATUS` queries are not overwritten by real connected/reconnect callbacks while the scene is being judged. `clear`, `off`, sleep, error, and real re-pair events clear that preview override.

## Driver Boundary

`status_led.c` owns the business state machine, semantic LED mapping, current budget, USB commands, and frame rendering. `status_led_strip_backend.c` owns physical strip output: RGB byte order, ESP-IDF RMT at 10 MHz, the WS2812 encoder, and a 300 us reset latch with 4020-compatible bit timing. This keeps a future LED hardware change below the backend boundary instead of leaking into BLE, keyboard, OTA, or recording logic.

The status LED task refreshes every 50 ms while active and sends only strip frames whose RGB data changed, so a stable status rail does not force the key strip to be retransmitted. When multiple strips do change, the status strip is transmitted last, and recording/processing frames with inactive `OK`/`WARN` use the guarded status-strip packet without extra repeat writes. Dynamic EC11/edge accent updates also include a final status-strip transmit while REC/AI are active, so LED5/6 are actively re-zeroed during advanced effects instead of relying on the previous status packet. The RMT strip backend resets the WS2812 encoder before every transmit and before retrying an invalid-state transmit, appends six extra black guard pixels after the real six status LEDs, and keeps BLE, OTA, keyboard scan, power manager, and diagnostics out of software bit-banging.

## Profiles And Budget

Profiles are persisted in NVS through `~LED:PROFILE <off|low|standard|ambient|factory>`. A separate user brightness cap is persisted through `~LED:BRIGHTNESS <0-100>` and applies as the hard routine-product brightness limit across the status, key, EC11, and edge zones. `~LED:BRIGHTNESS` remains a compatibility command and writes both device brightness profiles. New desktop/device settings should prefer `~DEVICE:SETTINGS` plus `~DEVICE:SET plugged_brightness=<0-100> battery_brightness=<0-100>` so plugged and battery operation can have different global caps, and `~DEVICE:SET led_status=<0-100> led_key=<0-100> led_ec11=<0-100> led_edge=<0-100>` when each physical LED zone needs its own maximum. Fresh devices default to plugged brightness 80%, battery brightness 50%, and 100% per-zone caps; animations may breathe below those caps but must not replace them with fixed hidden maxima.

User brightness scales the whole routine effect envelope before the profile cap is applied. A 50% user brightness setting scales the external-power breath's low and high points together, rather than clipping all samples above 50% into a flat line. The charging breath is intentionally shallow and slow so plugged-in charging reads as alive without pulling attention like a warning or recording state.

In firmware, `plugged_brightness` and `battery_brightness` are now applied as physical duty percentages (0-100% directly maps to the internal 0-255 output scale), which makes the numeric setting more predictable when you are tuning actual lamp intensity.

- `standard` is the product default. It does not add a hidden percent cap above the user plugged/battery brightness setting.
- `low` keeps low-power visual behavior and a smaller current budget, but the visible percent cap still comes from the user brightness setting.
- `ambient` permits restrained idle accent behavior when the EC11 and edge chains are available, without adding a hidden percent cap above the user brightness setting.
- `off` turns routine non-safety output off; safety/error/test paths can still light.
- `factory` keeps the full 100% profile path for calibration, manufacturing, and hardware bring-up; routine product effects still respect the user brightness cap unless they are explicit safety/error/test output.

Current is still estimated per frame with 20 mA per RGB channel at full scale. `standard`, `low`, and `ambient` have product budgets so broad multi-LED effects are dimmed by current budget when needed; those budgets are not a second fixed percent cap. Explicit safety/error/test paths retain the full bring-up budget. The renderer suppresses repeated RMT writes for unchanged frames and slows the task cadence in static idle states; state changes notify the task so button, recording, processing, and test feedback still appear promptly.

## Product Effect Language

- Active connected state is readable but not dominant: PWR/BLE confidence remains visible without using factory brightness. When `power_manager` enters connected or disconnected idle, routine status LEDs are turned off so an idle board does not keep the LED rail or RMT task active; the next real key/recording/processing/LED command resumes normal feedback.
- External power overrides battery-color display on `PWR`: USB plugged and not confirmed full is a continuous slow white breath with an 8%-38% product range while idle, so the difference between the low and high points is visible without feeling like a warning, recording state, or high-energy animation. During recording or processing, `PWR` holds a steady readable 28% white floor so it does not add another dynamic status-rail source. Charge-full requires USB present, an active charge-full pin, no active charging pin, and a near-full battery reading for the debounce window; after that it latches for the current USB session and shows steady white until USB is unplugged.
- The external-power white breath, full-charge steady white, BLE, REC, AI, OK, key feedback, EC11 accents, and edge/frame accents are routine product output and obey the active plugged/battery user brightness cap plus the matching per-zone maximum cap. Their animation curves may use lower intermediate levels, but their routine maximum is clipped by explicit user settings rather than a hidden profile constant.
- Pairing and reconnect use recognizable blue pulses without turning the whole status rail into an animation surface. Pairing and reconnect use only the `BLE` semantic LED, with the EC11 ring and edge/frame group off. User-requested re-pair/reset uses `BLE` plus a low blue EC11 confirmation orbit, while the edge/frame group stays off. A successful connected transition gets a short BLE-only blue confirmation. Re-pair must not light `LED6=WARN` unless the recovery operation actually fails.
- Recording is a controlled warm-gold semantic state on status `LED3=REC`; it does not borrow key LEDs and does not clear independent `PWR`/`BLE` status. Firmware still exposes `rec_level` in `~LED:STATUS` and accepts `~LED:REC_LEVEL <0-100> [hold_ms]` for repeatable review, but routine product rendering no longer uses PCM level to drive brightness because the current hardware shows LED5/6 tail disturbance under broad dynamic loads. During active recording/processing, `PWR` and connected `BLE` stay readable even after the ordinary status window expires. The semantic `REC` status LED uses a small slow 4%-quantized breath so it is alive but not noisy; the EC11 knob-base ring keeps all 12 LEDs on with a low warm-gold base plus a broad slow deterministic flow, and the edge/frame keeps all 6 LEDs on with a low warm-gold base plus a wider same-cycle clockwise flow so the frame does not read as missing LEDs or a static brightness bar. Starting a new recording clears any stale `OK` completion window and retryable recording warning in the same LED-state update, so `LED5=OK`/`LED6=WARN` cannot linger into active capture.
- Processing is a controlled saturated purple semantic state on `LED4=AI` once the desktop host starts streaming/ASR processing. The status `AI` LED uses a slow, 4%-quantized brightness breath instead of a moving status-rail animation. Processing-only EC11 and edge/frame use low violet clockwise motion with matched full-cycle timing. When recording and processing overlap, status `REC` and `AI` breathe independently at low amplitude, while EC11 and edge/frame give priority to the stable low warm-gold recording cue instead of same-zone gold/purple mixing; AI remains visible on status `LED4`. `LED1=PWR` and `LED2=BLE` keep their own state unless power/BLE state actually changes. Starting a new processing window clears stale `OK` and retryable AI/OTA warning windows before the first processing frame.
- Firmware recording transfer does not animate `AI` by itself. A successful local stop and a completed local recording session each refresh the green `OK` confirmation window so the device visibly acknowledges that recording ended. The desktop host starts processing with `VREC:PROCESSING:START`, can clear it with `VREC:PROCESSING:STOP`, and reports completion with `VREC:PROCESSING:DONE`; `DONE` turns `AI` off and flashes green `OK` again for a 2.0 second visible confirmation window.
- Key LEDs remain local transient feedback only: white while pressed with a short dim white release tail. Recording and processing no longer light the key strip, so keys do not compete with status semantics or the knob/frame accents.
- EC11 knob and edge/frame LEDs are independent accent surfaces. Standard profile uses restrained accents for recording-only, processing-only, OK, and physical EC11 input feedback; ordinary BLE pairing/reconnect states stay on the `BLE` semantic LED rather than using EC11 or edge/frame cues, while user-requested re-pair adds a low blue EC11 confirmation orbit. Ambient adds calm low-blue idle accents. The knob ring is allowed to feel richer than the status rail, but the current V2 hardware shows visible LED5/6 tail disturbance when broad high-brightness EC11/edge dynamics run beside REC/AI. Routine recording therefore keeps the EC11 ring fully present with a low warm-gold base and broad slow deterministic flow on all 12 LEDs, while the edge/frame group keeps a low warm-gold base and a wider same-cycle clockwise flow on all 6 LEDs. `rec_level` remains diagnostic input but does not change the product brightness envelope. Processing-only uses matched low violet clockwise motion on EC11 and edge/frame; overlap gives recording warm gold priority as a stable cue instead of same-zone gold/purple mixing. EC11 short press and rotation add a brief white confirmation on the EC11 ring after the HID action is queued. These accents never set status semantics and are suppressed below low battery except safety/error/test paths.
- Status-tail anti-flicker guard: every normal rendered frame starts from zero, renders `PWR`/`BLE`/`REC`/`AI`, then renders `OK`/`WARN`, and finally explicitly clears `LED5=OK` and `LED6=WARN` unless an actual success or active error window owns them. The backend then appends six black guard pixels to the status-strip packet, only retransmits strips whose RGB data changed, writes the status strip last when multiple zones change, and forces three final status transmits when REC/AI are active with `OK`/`WARN` off. `REC`/`AI` may breathe, but only through the capped 4%-quantized status helpers; the old broad status-rail dynamic path is not used. `~LED:STATUS detail=contract` reports `status_tail_guard_pixels=6`, `status_tail_reinforce=recording_processing`, `status_tail_reinforce_writes=3`, `strip_dirty_tx=1`, `status_tx_last=1`, `dynamic_active_accents=1`, `active_work_status_dynamic=1`, and `active_work_status_static=0`; if `detail=rgb` still shows `OK=0,0,0` and `WARN=0,0,0` while a camera sees LED5/LED6 flash like LED3/LED4, treat it as physical signal integrity, optical bleed, or physical mapping evidence, not as a semantic state bug.
- Long-press shutdown confirmation: when EC11 long press crosses the power-control threshold, firmware shows a warm amber pending cue by restoring LED output, holding `PWR` amber, and filling the EC11 ring clockwise over 1.8 seconds; the edge/frame group stays off for this confirmation. After one full ring, the pending cue stays latched at full ring instead of timing itself out; only final long-press hardware shutdown, sleep, clear, or another explicit state transition turns it off. When hardware shutdown is actually confirmed, firmware shows a short brighter amber full-ring cue before entering sleep. The confirmation cue temporarily takes priority over REC/AI decorative accents, while `PWR`/`BLE` state remains independently rendered before the cue.
- Warnings use `LED6=WARN` only. Retryable and hard error pulses do not borrow source LEDs, keys, EC11, or edge/frame accents, so an error is visually distinct from recording, processing, OK, and charging. Critical battery remains a dedicated `PWR` safety cue.
- The product palette favors clear semantic colors on the current diffuser: green for battery-good/OK, white for external power and local key feedback, blue for BLE, gold for recording, red for hard warning, amber for lower battery or retryable warning, and purple for AI.
- RGBW, map, chase, and pixel test commands remain calibration tools and can drive full brightness independent of the product profile.

- `~LED:PREVIEW pairing`, `~LED:PREVIEW reconnect`, and `~LED:PREVIEW repairing` exercise the BLE connection states used for first pairing, host reconnect, and EC11 double-click re-pair recovery. Pairing and reconnect keep EC11 and edge/frame off, with `LED2=BLE` carrying the connection cue. Reconnect keeps a low blue BLE floor with a brighter double-pulse. `repairing` should show `ble_repair_ms_left` in `~LED:STATUS`, keep `WARN` off unless a separate hard failure is injected, use BLE plus a low blue EC11 orbit for user-requested re-pair confirmation, and keep edge/frame off.
- `~LED:PREVIEW recording_processing` shows the connected ready baseline plus active capture and host-processing: `LED1=PWR` and `LED2=BLE` remain independent, `LED3=REC` and `LED4=AI` are added, EC11/edge show low deterministic warm-gold same-cycle flow accents, key LEDs stay off unless physically pressed, and `LED5=OK`/`LED6=WARN` must remain off unless a later success or fresh error command is sent. Run `~LED:STATUS` during this preview and inspect the `detail=rgb` line to verify the current render-sampled status frame, not just a camera frame.
- `~LED:PREVIEW recording_processing_status_only` uses the same status `PWR/BLE/REC/AI` semantics while suppressing key, EC11, and edge accents. Use it only as a diagnostic split: if status-only still flashes physical LED5/LED6 while `detail=rgb` reports `OK=0,0,0;WARN=0,0,0`, the remaining issue is on the status rail itself rather than multi-zone accent interference.
- Dedicated LED-effect tuning must use `~LED:PREVIEW capture_led_only`, `~LED:PREVIEW recording_processing_led_only`, `~LED:PREVIEW recording_processing_status_led_only`, or `~LED:PREVIEW processing_led_only`. These modes run the same product renderer but set `preview_effect_only=1`, keep PWR/BLE and physical key-press feedback out of the rendered frame, clear stale OK/WARN/error windows, and ignore live charge/BLE/key events for visual judgment. Full effect-only modes judge status, EC11, and edge together while the key strip stays off; status-only effect modes set `preview_suppress_accents=1` and keep key/EC11/edge off. Power samples may still update diagnostic readback, but they do not reset the effect phase or change `last_reason` during effect-only review. Use ordinary `capture`, `recording_processing`, and `processing` only for product-scene review where PWR/BLE participation is intentional.
- `~LED:PREVIEW recording_processing_status_key_stress` is a diagnostic-only repro pattern. It sets `preview_effect_only=1`, drives status `LED3=REC`/`LED4=AI` dynamically while keeping software `LED5=OK`/`LED6=WARN` at zero, and mirrors the status dynamics on the key strip without involving EC11 or edge LEDs. Use the narrower `~LED:PREVIEW status_key_stress3`, `~LED:PREVIEW status_key_stress4`, and `~LED:PREVIEW status_key_stress34` forms for human diagnosis: LED3+KEY1 isolates possible LED5 follow, LED4+KEY2 isolates possible LED6 follow, and LED3/4+KEY1/2 checks the two-channel threshold before the all-key stress.
- `~LED:PREVIEW shutdown_confirm` and `~LED:PREVIEW shutdown_final` exercise the pending and final long-press shutdown confirmation effects without requiring an actual power-off. For pending shutdown review, wait longer than 1.8 seconds and confirm the EC11 ring remains fully lit until `shutdown_final`, `sleep`, `clear`, or a real power-off path clears it.
- `~LED:ERROR <ble|recording|ai|ota|power|system> <retryable|hard>`
- `~LED:PROFILE <off|low|standard|ambient|factory>`
- `~LED:OFF` clears test/status output immediately and stays dark until the next status/key event. It is not the sleep path; `status_led_prepare_sleep()` remains the sleep-only full output disable.
- `~LED:WAKE`

When camera capture is not trustworthy, `tools/status_led_manual_calibration.ps1` drives one status/key LED RGBW/off command at a time at 100% brightness and records human-eye feedback under the step validation directory. For EC11/edge bring-up, use direct serial `~LED:TEST:PIXEL ec11 LED7 white 100`, `~LED:TEST:PIXEL edge LED17 white 100`, or full-strip `~LED:TEST:RGBW ec11 edge`/`~LED:CHASE ec11,edge`.

Real V2 hardware validation still has to record the actual RGB color order and physical LED order with photos or video. The firmware default color order is `GRB` for all four strips. Status/key use the 3528 WS2812-style part, while EC11/edge use the 4020 WS2812B part; both datasheets use 24-bit GRB data, but the 4020 part needs the longer reset latch and stricter low-time timing used by the backend.

During 2026-06-08 hardware bring-up, status/key LEDs responded on the current board but EC11/edge LEDs did not light after the firmware was flashed with the 4020-compatible timing above. Treat EC11/edge darkness as a separate hardware pinout or continuity investigation before changing firmware color order or WS2812 timing again.
