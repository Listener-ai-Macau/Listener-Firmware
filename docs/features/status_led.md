# V2 Status LED Firmware Contract

This firmware pass implements the V2/N16R8 status lighting as a centralized `status_led` component with a separate strip backend. Business code talks to semantic APIs such as `status_led_set_ble_state()` and `status_led_notify_key_event()`; it does not know whether the physical LEDs are WS2812, a future RGB driver, or another strip implementation.

> **Before changing the LED driver, DMA selection, or adding an LED peripheral, read [status_led_dma_history.md](status_led_dma_history.md).** It consolidates the historical tuning experience and explains why only the status strip is on DMA (ESP32-S3 has only one RMT-DMA channel), why DMA can not stay enabled through low-power idle, the flicker-free DMA output budget (1 RMT + 2 SPI = 3, or move the mic to I2S1 for LCD_CAM), and the guardrails any DMA change must respect.

## Hardware Resources

- `LED1`-`LED6`: semantic status rail on `PWM_RGB_Status`, `BOARD_PINS_RGB_STATUS_IO`, GPIO1.
- `LED7`-`LED10`, `LED15`-`LED16`, and `LED23`-`LED28`: EC11 12-LED knob ring on `PWM_RGB_EC11`, `BOARD_PINS_RGB_EC11_IO`, GPIO5.
- `LED11`-`LED14`: local key feedback on `PWM_RGB_KEY`, `BOARD_PINS_RGB_KEY_IO`, GPIO13.
- `LED17`-`LED22`: edge/frame group on `PWM_RGB_Edge`, `BOARD_PINS_RGB_EDGE_IO`, GPIO4.
- `GPIO14` is reserved for `BAT_CHG_IO` in the accepted V2/N16R8 board profile and must not be used for `PWM_RGB_KEY`.
- `VDD_LED` has no firmware-controlled enable pin in the current board contract. Firmware treats the rail as hardware-powered and exposes this as `vdd_led_enable=always_on_assumed` in `~LED:STATUS`.

## Semantic Rail

Default order is fixed until real hardware silkscreen validation proves otherwise:

- `LED1=PWR`
- `LED2=BLE`
- `LED3=REC`
- `LED4=AI`
- `LED5=OK`
- `LED6=WARN`

`PWR` owns battery and external-power state. While unplugged, it uses green for healthy battery, amber for medium/lower battery, steady red for low battery, and red double-flash for critical battery. While USB/VBUS is present, it uses white: a slow always-running breath while plugged in and not confirmed full, then steady white once charge-full has been debounced and latched for that USB session. `BLE` owns pairing, reconnect, active disconnected/no-host, Windows/HID-only connected Type-search, Listener-Type-ready, and user-requested re-pair confirmation. Pairing and ordinary reconnecting are visible blue attention pulses with a real dark off phase. Only ordinary HID-only `connected` keeps the low-floor blue double-flash Type-search cue while active, so the low valley means a real BLE connection exists but Listener-Type is not ready yet. Active disconnected/no-host stays dark; idle and explicit all-off are also dark, with PWR/other activity used to tell active no-host from idle. `TYPE_READY` remains the only steady connected blue state. `REC` only lights for a real capture/upload source named by firmware. If capture is unavailable, firmware shows only `WARN`. `AI` owns the local post-stop transfer/thinking window plus host-confirmed text processing, so it can start immediately after a stop key is accepted. `OK` is a visible 2.0 second success confirmation after the host reports processing done, and it is also the OTA-in-progress semantic LED using a distinct cyan/green pulse. `WARN` owns retryable and hard errors without borrowing source LEDs or decorative zones.

## BLE Connection Source Of Truth

GAP/HID connection state is the source of truth for the BLE semantic LED. Advertising is allowed to drive `pairing` or `reconnecting` only while the GAP layer has no active connection. If a stale advertising-complete or advertising-restart path fires after the host is already connected, firmware skips advertising and refreshes `connected` instead of allowing `pairing` to overwrite the LED state.

After a connected event, ordinary HID-only `connected` uses a continuous low-floor blue double-flash Type-search cue while active, so a Windows pairing/HID link reads as "looking for Type" until Listener-Type is actually ready or the power manager enters idle. `TYPE_READY` is the Listener-Type-ready BLE state: after Listener-Type heartbeat/readiness has been observed it uses steady blue in active mode. The audio transport still uses the strict 12 second heartbeat timeout for send/readiness decisions, but the LED has a 30 second Type-ready hold while active so routine host scheduling jitter does not visually bounce the BLE lamp; explicit `TYPE:BYE`/`TYPE:STOP`, notify disable, or BLE disconnect clears the hold immediately. Connected/disconnected low-power idle keeps PWR visible and leaves reconnecting/connected/TYPE_READY BLE dark; REC/AI/OK/WARN plus decorative zones stay off. Routine Listener-Type heartbeat timeout/restore only updates the semantic BLE state and must not reopen an active BLE window from idle. Pairing and user-requested re-pair remain the only low-power idle BLE attention cues. Battery idle keeps a Type-capped amber PWR fallback if the live battery sample is temporarily unavailable.

Manual preview and clear commands are not BLE source-of-truth events. If a test preview clears the BLE semantic state while HID remains connected, the next connected HID battery/status update resynchronizes the semantic state to `connected` or `TYPE_READY` without presenting HID-only `connected` as steady ready blue.

Repeated same-state BLE callbacks are idempotent: they do not restart the status window or confidence window. This prevents host subscription noise from making the PWR green status indication look like an irregular post-connect blink.

User-requested re-pairing, including EC11 double-click recovery and `~VREC:RECOVERY`, is a BLE connection flow rather than an error flow. It calls `status_led_notify_ble_repairing()`, clears stale REC/AI/OK state, opens the recovery pairing window, and deletes the firmware-side old peer asynchronously after disconnect before advertising can restart. If a recent Type heartbeat or Type-host presence window proves Listener-Type was active on this computer, EC11/USB recovery keeps the current stable BLE identity with the quiet Type pairing advertising profile and no Swift Pair payload so Windows does not show a competing native pairing toast. If Type is absent and no recent Type-host presence exists, native recovery rotates and persists a new static-random BLE identity before pairable advertising so Windows can create a fresh keyboard bond without Listener-Type. It gives `LED2=BLE` and the EC11 knob ring a synchronized three-cycle blue double-flash confirmation even if BLE was already pairing, so an accepted EC11 double-click is visibly acknowledged every time without lighting the key strip or edge/frame group. Native recovery exposes one bounded Swift Pair window so Windows keyboard pairing can recover without Listener-Type. The longer Windows pairing window can stay open after that confirmation, but it must not keep repeating the confirmation pattern forever. The host must create a new bond through the recovery window instead of silently treating the double-click as an ordinary reconnect to the old bond. Hard failures while opening the pairing window, rotating the native recovery identity, or restarting advertising still use `WARN` only.

## Flash Diagnostics

Unplugged/no-serial LED behavior must be reconstructed from flash-backed diagnostics after reconnect, not from live serial output. The status LED component persists `DIAG_LED_POWER_INPUT`, `DIAG_LED_VISUAL_STATE`, `DIAG_LED_OUTPUT_STATE`, and `DIAG_LED_FRAME_RGB` so a post-reconnect dump can show LED-side power/charge/full flags, raw and display-latched battery level, suppressed battery-only display rises, PWR RGB and color class, active PWR/BLE/REC/AI/OK/WARN bits, EC11/edge presence, status color classes, output intensity summaries, and output disable/resume transitions. Raw battery readings remain unchanged for diagnostics and safety; the PWR battery color uses the display-latched level so battery-only voltage rebound cannot flip amber/green.

For the USB-unplug light-cycle issue, a PASS or root-cause claim must cite decoded `summary.param_highlights.status_led.power_input`, `status_led.visual_state`, `status_led.output_state`, optional `status_led.frame_rgb`, `power.external_power`, and `power.sleep_wake` event refs from the unplugged interval. Dump flash diagnostics with `tools/dump_diag_log.ps1`, decode with `tools/decode_diag_log.py`, then validate the decoded bundle with `tools/verify_unplugged_flash_diag_bundle.py --expect-pwr-class amber --expect-pwr-class green` when reproducing the observed yellow/green PWR cycling.

`~LED:STATUS` prints a bounded set of detail lines. Its `detail=power` line reports `external_power_source=usb_det|charger_status|none`. `usb_det` is the normal VBUS divider path; `charger_status` is a visual fallback for boards where `BAT_CHG_IO` proves the charger is active while `USB_DET/GPIO7` reads low. This prevents a plugged board from falling back to battery-only PWR/BLE behavior while charging. Its `detail=rgb`, `detail=rgb_ec11`, `detail=rgb_key`, and `detail=rgb_edge` lines print a current render-sampled RGB frame for all four LED zones so short BLE pulses and effect-only previews can be logged at the moment the status command is handled, not only from a previous refresh cache.

## Status/Key Mapping Calibration

The camera calibration contract for the first product pass is intentionally limited to the ten status/key LEDs:

- `LED1=PWR`, `LED2=BLE`, `LED3=REC`, `LED4=AI`, `LED5=OK`, `LED6=WARN` on the status strip.
- `LED11=KEY1`, `LED12=KEY2`, `LED13=KEY3`, `LED14=KEY4` on the key strip.

The status and key strips keep separate color-order storage in firmware, both defaulting to `GRB` until camera validation proves a different order for either strip. `~LED:STATUS` exposes `mapping_contract`, `status_physical_map`, `key_physical_map`, `separate_status_key_color_order=1`, `status_query_samples_current_render=1`, and power diagnostics including `raw_charging`, `raw_full`, `full_latched`, and `full_candidate_ms` so static and serial checks can reject EC11/edge assumptions and explain charge-state pin jitter before camera capture.

The status command is intentionally split into bounded `detail=contract|brightness|strips|state|power|rgb|summary` lines; tools should parse the final `detail=summary` line for semantic state and use the earlier detail lines for diagnostics. `detail=contract` reports `task_priority=6`, `task_core=1`, `task_affinity=cpu1`, `startup_complete_gate=ble_visible_ready_frame_no_early_pwr_normal`, `reset_us=300`, `rmt_reset_us=300`, `spi_reset_us=600`, `spi_ws2812_waveform=4bit_3m2_0x8_0xE`, `strip_transport_requested=status:rmt,ec11:spi2,key:spi3,edge:rmt`, `strip_transport_actual`, `spi_dma_requested`, `spi_dma_actual`, `spi_dma_fallback`, `rmt_tx_dma_supported`, `rmt_tx_dma_strategy=status_strip_dma_full_frame_buffer`, `rmt_strip_all_available`, `rmt_tx_dma_all_strips=0`, `low_power_status_tx=non_dma_clear_and_final_frame`, `low_power_all_zone_tx=non_dma_clear_and_final_frame`, `key_dark_idle_resync_ms=0`, `key_tail_guard_pixels=0`, `key_dark_latch_rmt_writes=2`, `key_dark_latch_expiry_dirty=1`, `key_dark_clear_tx=spi_dma_prelatch_then_one_shot_rmt_gpio_low`, `key_lit_edge_tx=spi_dma_only`, `key_feedback_dynamic_tx=spi_dma_until_dark_latch`, `key_single_white_hold_ms=160`, `key_multi_key_independent_fade=1`, `strip_tx_failure_retry_dirty=1`, `suspended_strip_resume_dirty=1`, `shutdown_final_status_tx=dma_visible_pwr_no_black_latch`, `shutdown_final_all_zone_tx=non_dma_pwr_only_latch_or_all_off`, `low_power_final_latch_writes=3`, and per-strip RMT-only `rmt_tx_dma_requested`, `rmt_tx_dma_actual`, `rmt_tx_dma_fallback`, and `rmt_mem_block_symbols`. On the current ESP32-S3 V2 hardware the active expected RMT pattern is `rmt_tx_dma_requested=status:1,ec11:0,key:0,edge:0`, `rmt_tx_dma_actual=status:1,ec11:0,key:0,edge:0`, and `rmt_mem_block_symbols=status:1024,ec11:0,key:0,edge:48`; low-power latch frames clear every strip off its DMA transport before suspend so physical WS2812 latch state cannot survive quiet idle, while shutdown-final keeps the visible PWR/status frame on the normal DMA path and only uses the dark latch for non-PWR strips. Interactive resume transition clears reacquire active transports so EC11/KEY feedback starts on SPI DMA. If a strip transmit fails after `last_frame` is updated, firmware keeps that strip dirty and retries it on the next refresh instead of allowing unchanged-frame suppression to hide a partial physical latch. If a strip was deliberately suspended after an idle/final latch frame, the next non-final refresh treats it as dirty even when RGB data is unchanged, so unchanged-frame suppression cannot leave EC11/key physically unavailable until power-cycle. The active expected SPI pattern is `spi_dma_requested=status:0,ec11:1,key:1,edge:0`, `spi_dma_actual=status:0,ec11:1,key:1,edge:0`, and `spi_dma_fallback=status:0,ec11:0,key:0,edge:0`. If SPI init fails on either EC11 or key, firmware falls that strip back to non-DMA RMT and reports the affected `spi_dma_fallback` bit. After low-power idle suspends LED transports, actual DMA fields may report zero until the next active LED frame reacquires the transport. Future DMA changes must update this contract only with physical validation evidence instead of silently changing the current board behavior.

`detail=strips` repeats each physical strip with `transport`, `avail`, generic `dma_req`/`dma`/`dma_fb`, plus explicit `rmt_dma_*` and `spi_dma_*` markers. `detail=summary` reports separate `PWR`/`BLE`/`REC`/`AI`/`OK`/`WARN`/`EC11`/`KEY`/`EDGE` active flags so semantic status, local key feedback, knob accents, and frame accents can be judged independently. Re-pair uses a BLE-plus-EC11 confirmation cue, so `ble_repair_ms_left` should be nonzero during the bounded user-requested re-pair window, `active_flags` should include `BLE` and `EC11` but not `KEY`/`EDGE` for that cue, and then return to `0` while ordinary `ble=pairing` carries the ongoing semantic state. `detail=state` and `detail=summary` report `shutdown_confirm_active`, `shutdown_confirm_latched`, and `shutdown_confirm_elapsed_ms` so a pending shutdown cue can be verified even if a live power sample updates `last_reason`; the non-final EC11 shutdown ring fills from zero over the full confirmation window instead of pre-lighting the first pixel and finishing early. `detail=state`, `detail=power`, and `detail=summary` report `preview_ble_override_ms_left` during manual product-scene preview. `detail=state` and `detail=summary` also report `preview_effect_only`, which must be `1` during dedicated LED-effect tuning runs that intentionally suppress PWR/BLE rendering and live power/BLE interference. `detail=brightness` and `detail=summary` also expose `budget_scale_percent` and `budget_limited_by_current` so you can confirm whether a requested 0-100 brightness is being reduced by current limiting. The manual `TEST:PIXEL` path can also address EC11 and edge/frame LEDs for hardware bring-up, while the first camera mapping contract remains limited to status/key.

BLE animation phase is tracked separately from generic visual transitions. `detail=power` reports both `ble_transition_ms` and `last_transition_ms`; `power_change` may refresh the PWR/status window on a plugged board, but pairing, reconnecting, re-pair, and connected Type-search BLE pulses use the BLE phase so charge-state polling cannot restart or hide the connection cue.

Manual `~LED:PREVIEW` scenes temporarily hold their requested BLE state for 15 seconds, so human review popups and their repeated `~LED:STATUS` queries are not overwritten by real connected/reconnect callbacks while the scene is being judged. `clear`, `off`, sleep, error, and real re-pair events clear that preview override.

## Driver Boundary

`status_led.c` owns the business state machine, semantic LED mapping, current budget, USB commands, and frame rendering. `status_led_strip_backend.c` owns physical strip output for all four physical zones: status, EC11 knob, key, and edge/frame. The shared backend owns RGB byte order, ESP-IDF RMT at 10 MHz, per-strip RMT DMA selection, the WS2812 encoder, the SPI MOSI clock-hack transport for EC11/key, a 300 us RMT reset latch, and a 600 us SPI reset-low tail with 4020-compatible bit timing. The SPI WS2812 waveform is the conservative 4-bit 3.2 MHz code `0=1000`, `1=1110`, giving active KEY frames a longer zero-low window than the older 3-bit 2.5 MHz code. The current V2 hardware keeps advanced status REC/AI effects on the status RMT-DMA path, drives EC11 from SPI2 DMA, drives key from SPI3 DMA, and leaves edge/frame on ordinary RMT. If SPI DMA initialization fails on EC11 or key, the affected strip falls back to non-DMA RMT and reports `spi_dma_fallback=1`. Low-power entry/resume and stable-idle final PWR-only latch frames temporarily use non-DMA transports for every strip, because live idle validation showed DMA-backed LED outputs could leave physical LEDs latched on while firmware rendered only PWR/BLE. The key strip does not get periodic dark retransmits during idle; a KEY feedback transition to all-dark sends an SPI3 DMA pre-latch followed by a bounded two-write RMT black latch and GPIO-low release with no normal tail guard pixels, then stays quiet. Lit white/purple KEY feedback and fade frames stay on SPI3 DMA; 2026-07-08 human review showed even a single lit-edge one-shot RMT/GPIO-low latch could make later physical key pixels flash when KEY1 was pressed. A later same-day review showed active SPI frames still needed the 4-bit waveform because the old 3-bit zero code could let KEY1 bring up following key pixels. The accepted KEY fix preserves the old effect instead of masking hardware issues with visual mutual exclusion: single-click feedback keeps a 160 ms white confirmation before purple, and different keys may overlap as independent fades rather than clearing each other. 2026-07-03 live A/B showed adding six KEY tail guard pixels makes KEY3 red couple into KEY4, while `key_tail_guard_pixels=0` restores the original one-pixel behavior. 2026-07-07 live key3/key4 follow-up kept the SPI3 DMA path but doubled its reset-low tail from about 300 us to about 600 us, because product-state logs showed key `px3/px4` rendered dark while downstream physical key LEDs could still visibly follow dynamic frames. 2026-07-08 KEY4 residual-live-status evidence showed firmware `key_rgb px4:0` and `key_mask=0x00` while the physical last key could remain latched, so only the all-dark one-shot latch now writes the black RMT frame twice before releasing GPIO; accepted white-to-purple and fade timing remain unchanged. Future DMA changes stay below the backend boundary and need both physical idle-latch evidence and advanced-effect flicker evidence before being exposed.

The status LED task runs at priority 6 pinned to CPU1 and refreshes every 50 ms while active. It sends only strip frames whose RGB data changed, so a stable status rail does not force other zones to retransmit, and EC11/edge accent-only motion does not repeatedly refresh the status rail. When multiple strips do change, the status strip is transmitted last. Recording/processing frames with active `REC`/`AI` and inactive `OK`/`WARN` normally repeat the status-strip packet only when the status RGB data itself changed, using the black tail guard to reinforce LED5/6 at zero. REC+AI overlap is the exception: it may use a very slow 1%-step in-phase LED3/4 brightness change, but it sends each changed status frame only once so the overlap animation does not multiply tail disturbance. BLE pairing and connected-confirmation cues are capped near the steady connected blue level rather than using a full-bright blue spike, which keeps the BLE transition visible without lighting the shared status diffuser hard enough to look like all six status LEDs are flashing. Active pairing and ordinary reconnect pulse through dark frames; HID-only connected Type-search keeps the visible low-floor blue pulse whose peak maps to the Type status cap. Disconnected/no-host stays dark, and the synchronized BLE-plus-EC11 three-cycle double-flash is reserved for user-requested re-pair confirmation. The RMT strip backend can use SOC-supported TX DMA when a strip selects it, resets the WS2812 encoder before every transmit and before retrying an invalid-state transmit, appends six extra black guard pixels after the real six status LEDs, and keeps BLE, OTA, keyboard scan, power manager, and diagnostics out of software bit-banging. The KEY SPI3 strip intentionally uses zero tail guard pixels; it relies on changed SPI3 frames, the 600 us SPI reset-low tail, and the existing low-power all-zone clear path.

Bring-up lesson: WS2812-style LEDs latch the last complete color frame, but the data line still needs a defined idle level after the frame is sent. On the V2 status rail, live evidence showed the DMA status path could corrupt the tail of an otherwise PWR-only idle frame, leaving physical LED3-LED6 on while `detail=rgb` reported them off. Active BLE/recording/processing frames keep the status DMA channel enabled between changed frames so `.eot_level = 0` holds the line low without repeated enable/disable edges. Low-power stable idle first sends a non-DMA zero clear frame, keeps the transport alive through the 80 ms clear-to-final gap, then sends the non-DMA PWR-only status frame three times before releasing all four LED transports and driving each data GPIO low. Low-power may decide which semantic LEDs stay visible, but it must not own brightness or apply a hidden dimming layer; lit low-power PWR/BLE cues still use the Type four-zone brightness caps and status RGB energy balance. The LEDs keep the final PWR-only latch while firmware avoids low-power DMA retransmits or enabled idle windows that can corrupt the status rail into an all-on state. Full sleep/manual all-off still suspends all strips after transmitting black. Do not switch the status data pin to ordinary GPIO between normal active frames, and do not disable RMT after every successful dynamic frame; either pattern can create WS2812-visible pulses and flash LED3-LED6. Preview state changes schedule repeated zero status frames when leaving non-idle accents or BLE attention states, so stale LED3-LED6 data is cleared before the next effect. The 2026-06-23 active-DMA/idle-non-DMA decision and evidence are recorded in [status_led_active_dma_idle_nondma_stability_20260623.md](../validation/status_led_active_dma_idle_nondma_stability_20260623.md). If `~LED:STATUS detail=rgb` reports only PWR/BLE active while LED3-LED6 physically flash during an idle transition, check RMT idle-drive behavior and the status DMA policy before changing semantic rendering.

AI change guardrail: do not "fix" idle all-on by globally disabling status-strip DMA or by routing ordinary active transition clear frames through the non-DMA path. The only frames allowed to force non-DMA across strips are quiet low-power and prepare-sleep all-off latch frames. Shutdown-final keeps the PWR/status strip on the normal DMA path and uses the non-DMA dark latch only for non-PWR strips. Interactive resume may still schedule an all-zone transition clear, but that clear must reacquire active transports so EC11/KEY feedback starts on SPI DMA rather than the temporary RMT one-shot path. Do not suspend transports after the low-power clear frame; suspend only after the repeated final low-power latch. Normal active preview/effect switching, including clear frames used between REC/AI/OK/WARN previews, must stay on active DMA from the first active frame. The intended code shape is `force_non_dma = pwr_only_final_latch`, with `shutdown_final_all_zone_latch_needed` forcing the transmit mask to all strips once per final shutdown window so stale physical EC11/key/edge state cannot survive the final cue without continuously reinitializing those transports while PWR changes.

Shutdown final contract: `~LED:STATUS detail=contract` reports `shutdown_final_status_tx=dma_visible_pwr_no_black_latch` and `shutdown_final_all_zone_tx=non_dma_pwr_only_latch_or_all_off`. Final hardware-shutdown confirmation clears every non-PWR LED on every strip, keeps the Type-capped PWR-only status frame on the normal status-strip DMA path to avoid an intermittent black handoff, and uses the non-DMA dark latch only for non-PWR strips. Automatic PWR_HOLD shutdown holds this final amber cue until power removal or failure recovery; it must not insert an all-off black window before driving PWR_HOLD. Ordinary active REC/AI/effect switching remains on active DMA.

## Profiles And Budget

Profiles are persisted in NVS through `~LED:PROFILE <off|low|standard|ambient|factory>`. Product brightness is controlled only by the four Type/device zone caps: `led_status`, `led_key`, `led_ec11`, and `led_edge`. `~LED:BRIGHTNESS <0-100>` is legacy compatibility that maps to all four zone brightness caps; it must not recreate a separate product-wide cap. New desktop/device settings should prefer `~DEVICE:SETTINGS` plus `~DEVICE:SET led_status=<0-100> led_key=<0-100> led_ec11=<0-100> led_edge=<0-100>`. Fresh devices default the status rail and key zone to 80%, while EC11 and edge/frame zones default to 100%; legacy plugged/battery brightness fields remain neutral diagnostics and are normalized to 100 at runtime. Animations may breathe below the zone caps, and their low points scale with the configured zone maximum rather than using a hidden fixed minimum.

Type zone brightness maps each named effect's design peak to the Type zone cap, then preserves the effect's own percent curve below that peak. A 50% Type zone setting means the active effect's high point is 50%, while low points, tails, and intermediate samples scale proportionally below it. This must not be implemented by normalizing every rendered frame to its current peak, because that erases fade tails and makes gradual key feedback disappear abruptly. Status-strip mixed RGB colors are then balanced so their channel sum matches the single-channel peak instead of letting white, purple, orange, or other multi-channel colors emit more total LED energy than blue/red/green at the same Type setting. The charging breath is intentionally shallow and slow in shape, but its high point still comes from the matching Type zone setting unless the current budget clamp has to reduce the frame for safety.

PWR, BLE, KEY, and OTA status cues all use that design-peak mapping in active and low-power states. For example, Type-ready blue keeps the same steady timing, but its configured high point follows `led_status`; KEY press/gesture feedback keeps the original fade shape, but its high point follows `led_key`. Low-power does not have separate brightness constants; it only changes which semantic LEDs remain visible and which LED transports are suspended.

In firmware, legacy `plugged_brightness` and `battery_brightness` commands are compatibility aliases that map to the four zone caps and keep the old plugged/battery fields neutral at 100.

- `standard` is the product default. It does not add a hidden percent cap above the Type-controlled zone caps.
- `low` keeps low-power visual behavior and a smaller current budget, but the visible percent cap still comes from the matching Type zone cap.
- `ambient` permits restrained idle accent behavior when the EC11 and edge chains are available, without adding a hidden percent cap above the zone cap.
- `off` turns routine non-safety output off; safety/error/test paths can still light.
- `factory` keeps the full 100% profile path for calibration, manufacturing, and hardware bring-up; routine product effects still respect zone caps unless they are explicit safety/error/test output.

Current is still estimated per frame with 20 mA per RGB channel at full scale. `standard`, `low`, and `ambient` have product budgets so broad multi-LED effects are dimmed by current budget when needed; those budgets are not a second fixed percent cap. Explicit safety/error/test paths retain the full bring-up budget. The renderer suppresses repeated RMT writes for unchanged frames and slows the task cadence in static idle states; state changes notify the task so button, recording, processing, and test feedback still appear promptly.

## Product Effect Language

- Steady connected state is Type-gated: ordinary HID-only `connected` uses a continuous low-floor blue double-flash Type-search cue while active, while `TYPE_READY` is steady blue so Listener-Type readiness is the only steady connected BLE indication. When `power_manager` enters connected or disconnected idle, routine active-work LEDs are cleared, reconnecting/connected/TYPE_READY BLE turns off, and only the Type-capped PWR indicator remains visible; pairing and user-requested re-pair can still blink BLE as attention states. REC/AI/OK/WARN, key, EC11, and edge/frame stay off until a real key/recording/processing/LED command resumes normal feedback. Low-power idle keeps the same Type zone brightness and status RGB energy-balance contract as active mode for every visible PWR/BLE cue; it does not own separate 12%/4% dimming constants. Low-power idle sends the final PWR-only status frame before immediately suspending the LED transports, so quiet idle does not keep retransmitting BLE or status frames.
- External power overrides battery-color display on `PWR`: USB plugged and not confirmed full is a continuous slow white breath with an 8%-38% product range while idle, so the difference between the low and high points is visible without feeling like a warning, recording state, or high-energy animation. During recording, processing, or OTA, `PWR` holds a steady readable 28% white floor so it does not add another dynamic status-rail source. Charge-full requires USB present, an active charge-full pin, no active charging pin, and a near-full battery reading for the debounce window; after that it latches for the current USB session and shows steady white until USB is unplugged.
- The external-power white breath, full-charge steady white, BLE, REC, AI, OK, key feedback, EC11 accents, and edge/frame accents are routine product output and obey the matching Type-controlled zone maximum cap. Their animation curves may use lower intermediate levels, and those minimum/intermediate levels scale with the zone maximum rather than using a separate global brightness or hidden profile constant.
- Pairing, reconnect, and HID-only connected Type-search use recognizable blue pulses without turning the whole status rail into an animation surface. Pairing, reconnect, and HID-only connected use only the `BLE` semantic LED, with the EC11 ring and edge/frame group off unless the user is actively pressing or rotating EC11. Active pairing and ordinary reconnect include a dark off phase; HID-only find-Type keeps a visible low blue floor between peaks while active. Low-power reconnect and active disconnected/no-host remain dark. User-requested re-pair/reset uses `BLE` plus the EC11 knob ring for a synchronized three-cycle blue double-flash confirmation; key and edge/frame stay off for that cue. A successful Type-ready transition is the steady blue connected indication. Plain Windows/HID-only connected uses a continuous low-floor blue double-flash Type-search cue and must not be steady blue or go dark while active. Re-pair must not light `LED6=WARN` unless the recovery operation actually fails.
- Recording uses `rec_level` only for status `LED3=REC`; it does not borrow key LEDs and does not clear independent `PWR`/`BLE` status. Firmware exposes `rec_level` in `~LED:STATUS` and accepts `~LED:REC_LEVEL <0-100> [hold_ms]` for repeatable review. The visual envelope is smoothed, rate-limited, and quantized before rendering. EC11, key, and edge/frame do not follow PCM brightness; they keep their own low-load product accents. During active recording/processing, `PWR` and connected `BLE` stay readable even after the ordinary status window expires. Starting a new recording clears stale `OK` and retryable recording warning state so `LED5=OK`/`LED6=WARN` cannot linger into active capture.
- Processing uses status `LED4=AI` immediately after firmware accepts a recording stop and when the desktop host starts streaming/ASR processing. The status `AI` LED stays purple and uses a brightness-only grouped da-dada thinking beat rather than a plain breath; the exact scan parameters live in the code constants and `~LED:STATUS detail=contract`, not in this prose. When recording and processing overlap, status `REC` follows the bounded audio envelope while status `AI` keeps the thinking cue; both stay on the dedicated status strip and overlap frames still use only one status-strip write. EC11 and edge/frame give priority to the stable low warm-gold recording cue instead of same-zone gold/purple mixing, and AI remains visible on status `LED4`. `LED1=PWR` and `LED2=BLE` keep their own state unless power/BLE state actually changes. Starting a new processing window clears stale `OK` and retryable AI warning windows before the first processing frame.
- OTA progress is not an AI processing state. `firmware_ota_begin()` starts an independent OTA visual with `LED5=OK` cyan/green pulse, EC11 ring progress fill plus a moving head, and a low cyan/green edge/frame chase. If the total image size is known, EC11 fill reflects bytes written; if the size is unknown, the ring keeps a moving alive cue. OTA completion turns the OTA visual off and uses the normal green OK success window; OTA verify, set-boot, write, or abort failures turn the OTA visual off and use `LED6=WARN`. While OTA is active, firmware holds `POWER_MANAGER_BLOCKER_OTA`, so connected/disconnected idle and hardware shutdown must not take over the LED strips or suspend the transfer. `~LED:STATUS detail=state` and `detail=summary` report `ota_active` and `ota_progress_percent`; OTA must leave `processing=0` and `active_flags` must not report `AI` unless a separate real AI processing state is active.
- Firmware recording transfer starts `AI` locally as soon as stop is accepted, so releasing the stop key has immediate thinking feedback while the final audio tail is delivered. The desktop host can refresh processing with `VREC:PROCESSING:START`, clear it with `VREC:PROCESSING:STOP`, and report completion with `VREC:PROCESSING:DONE`; `DONE` turns `AI` off and flashes green `OK` for a 2.0 second visible confirmation window.
- Key LEDs remain local transient feedback only: active-mode raw press feedback gives an immediate local white preview, stable press/release keeps the physical white acknowledgement, and any fallback white release tail fades smoothly from the release brightness to 0 instead of holding one low level and snapping off. KEY1-KEY4 intentionally use active-low light-sleep wake plus a 10 ms active scan and 20 ms elapsed-time debounce for press/hold detection, not runtime GPIO interrupts; restoring a runtime key GPIO ISR can create interrupt storms and reset the board during press/hold. Single-click local feedback keeps a short white confirmation before purple so the accepted white-to-purple handoff is visible, but the actual F13-F16 single HID dispatch still waits for the shared 500 ms double-click decision window; when that delayed single fires it must not restart the already-visible purple cue. Confirmed gesture feedback uses a bright purple with distinct timing: single click is one visible flash, double click is two visible flashes, and long press stays solid purple while the key remains held. KEY1-KEY4 and EC11 push share a 500 ms double-click decision window so the physical gesture timing stays consistent across all buttons. A KEY1-KEY4 tap that releases before the next same-level sample but has already held for the 20 ms debounce threshold is promoted through the normal stable press/release path so continuous four-key cycling is not lost to sampling phase. A sub-20 ms tap remains a raw-only transient: it may show the immediate white preview, but raw-only release must cancel that preview without a white release tail, HID dispatch, or purple single/double feedback. Starting any purple gesture confirmation clears only that same key's white release tail; different keys keep independent fade ownership, so a fast KEY1-KEY4 cycle may show one key fading purple while the next key shows white instead of using cross-key blackouts to hide follow-light. Once the visible purple flash pattern is complete the key LED must be released so a following physical press can show white immediately instead of being swallowed by a stale black feedback tail. Long press release refreshes the purple long confirmation for 1000 ms, matching the 1000 ms white-to-purple hold threshold, and it must not fall back to a white release tail after a held gesture. In low-power idle, KEY1-KEY4 wake edges only record activity until the 20 ms scan/debounce path confirms the key is still held; a latched-but-released wake edge is ignored instead of lighting the key strip or synthesizing a click. Recording and processing do not borrow the key strip for status semantics, and starting recording, stopping recording into processing, or starting processing must not clear or black-frame an in-flight KEY1-KEY4 press/release or purple gesture window. Physical KEY1-KEY4 press/release and confirmed gesture feedback must still light locally even if the resulting custom action is blocked.
- EC11 knob and edge/frame LEDs are independent accent surfaces. Standard profile uses restrained accents for recording-only, processing-only, OK, and physical EC11 input feedback; re-pair deliberately uses the product's synchronized BLE plus EC11 knob cue without borrowing key or edge/frame LEDs. Ordinary BLE pairing and active reconnect stay on the `BLE` semantic LED rather than using EC11 or edge/frame cues, while low-power reconnect stays dark. The accepted user-requested re-pair uses a synchronized BLE and EC11 three-cycle double-flash.

  EC11 push keeps the same 20 ms debounce model and 500 ms double-click decision window as KEY1-KEY4. Raw active-mode press still gives an immediate local white knob cue, but the confirmed single click waits for the full shared recovery decision window before sending the safe runtime `Shift+F13` fallback so an idle double-click cannot start recording first. A second real press inside that window accepts BLE re-pair recovery after a 60 ms raw-bounce guard; EC11 only differs in the mapped actions: confirmed single click sends the safe runtime `Shift+F13` fallback, double click opens BLE re-pair recovery, and long press still escalates to the amber shutdown confirmation after 0.8 seconds. The white EC11 press cue yields instead of overwriting existing EC11 recording, processing, OTA, visible re-pair cue, rotation, ambient, shutdown, or error effects. The EC11 push GPIO uses active-low light-sleep wake plus a bounded 20 ms scan for active and low-power waits; its runtime any-edge IRQ only latches the task awake and must not run click/recovery business logic in ISR context. EC11 A/B rotation keeps active edge IRQs and a 20 ms low-power backup poll; in low-power idle, any valid rotation edge resumes LED output and refreshes the white rotation cue, while each completed detent still dispatches the configured HID consumer action. Continuous rotation is direction-driven and fixed-step rendered: partial encoder edges refresh the current white head and update direction from the accumulated detent direction, so a single opposite contact-bounce edge cannot flip the cue; each accepted detent seeds the current head and extends the hold window, and the renderer then advances the white head at `STATUS_LED_EC11_ROTATION_STEP_MS` with a directional trailing arc. This keeps the cue visibly moving during a continuous turn instead of restarting at the first LED or going dark between detents, and reversing direction preserves the current head while flipping the trail immediately after the accumulated direction really changes. Avoid restoring detent-only, symmetric-tail, per-edge restart, or raw single-edge direction behavior; those regress the observed knob feel. The input path compresses duplicate raw ISR states, remembers the latest overflow state, and rereads physical A/B after draining a burst; HID consumer backpressure during fast rotation is log-only and must not light `LED6=WARN` because the local EC11 cue already acknowledged the action. If a very light active-mode EC11 tap produces the raw white press cue but releases before the 20 ms stable-press threshold, firmware treats it as a raw-only short click and still schedules the same pending single/recovery decision. BLE recovery double-click must require that second real raw/stable press candidate; a raw-only release by itself must not accept recovery, and sub-60 ms contact bounce must not become a recovery double-click. Debounce, the 500 ms pending single-click/custom-key response and recovery double-click guard, and the 0.8 second long-press threshold use real FreeRTOS elapsed ticks rather than poll-loop counts, because wake/poll churn must not make a short click look like a hold, treat contact bounce as recovery double-click, or expire either click window early.

  EC11 double-click recovery is not a key-style purple gesture: after the second click is accepted within the recovery window, recovery uses the synchronized blue three-cycle double-flash on `LED2=BLE` and the EC11 knob ring, while key and edge/frame stay off unless separate physical input feedback is active. Ambient adds calm low-blue idle accents. `rec_level` drives only status `LED3=REC`; processing-only uses matched low violet clockwise motion on EC11 and edge/frame; REC+AI overlap gives recording warm gold priority with the same low-load EC11/edge flow instead of same-zone gold/purple mixing. EC11 short press and rotation add a brief white local confirmation when no recording/re-pair/OTA/OK effect owns the knob ring; active recording keeps the warm gold EC11 flow above white local feedback. HID delivery is best effort and must not swallow the local light effect. These accents never set status semantics and are suppressed below low battery except safety/error/test paths.
- EC11 fast-rotation diagnostics are intentionally bounded: rotation feedback may write a flash-backed status diagnostic at most once per 500 ms, and the BLE HID usage queue must remain deep enough for short rotation bursts. High-rate diagnostic writes or shallow HID queues are regressions because they can make the local ring cue fade out while the user is still turning.
- EC11 rotation uses a longer low-tail hold than a press cue: accepted rotation input refreshes the visible floor, the renderer advances the head at the fixed rotation step while the hold remains active, and the rendered ring remains alive through short slow-turn gaps before fading out. Interactive wake from manual-off or low-power idle must schedule an all-zone transition clear before rendering fresh EC11/key feedback, because stale physical latch state can survive while the semantic frame is dark. Routine active-mode transition cleanup stays scoped to non-KEY accents so an in-flight key cue is not swallowed. Removing this rotation hold, using the shorter press fade, or skipping the all-zone resume clear can make the ring and status LEDs go black mid-turn, relight stale status LEDs, or restart on the next detent.
- Status-tail anti-flicker contract: every normal rendered frame clears `LED5=OK` and `LED6=WARN` unless an actual success, active OTA progress, or active error window owns them. The backend appends six black guard pixels, suppresses unchanged strip retransmits, writes the status strip last, and keeps the data line driven low between active changed frames without switching the GPIO mux or disabling RMT on every frame. Low-power stable idle sends a non-DMA final clear/PWR-only sequence, keeps the transport alive between clear and final latch, then suspends status, EC11, key, and edge transports with all data GPIOs driven low immediately after the repeated final latch. The first active refresh after such a suspend marks suspended strips dirty even if the rendered RGB frame is unchanged, which forces EC11/key to reacquire SPI DMA instead of staying unavailable or half-lit until a power-cycle. Dark key pixels are not periodically rewritten during idle, because repeated SPI dark frames can show up physically as red flicker; when key feedback transitions to all-dark, firmware sends an SPI3 DMA black pre-latch followed by a bounded two-write RMT black latch/GPIO-low release with `key_tail_guard_pixels=0` and then leaves the strip quiet. KEY lit white/purple/fade frames stay on SPI3 DMA until the final all-dark latch; any lit one-shot RMT latch is forbidden because live KEY1 review showed it can still bring up following physical key pixels. `~LED:STATUS detail=contract` reports `task_priority=6`, `task_core=1`, `spi_ws2812_waveform=4bit_3m2_0x8_0xE`, `strip_transport_requested=status:rmt,ec11:spi2,key:spi3,edge:rmt`, `strip_transport_actual`, `spi_dma_requested=status:0,ec11:1,key:1,edge:0`, `spi_dma_fallback`, `rmt_tx_dma_strategy=status_strip_dma_full_frame_buffer`, `rmt_tx_dma_all_strips=0`, `low_power_status_tx=non_dma_clear_and_final_frame`, `low_power_all_zone_tx=non_dma_clear_and_final_frame`, `key_dark_idle_resync_ms=0`, `key_tail_guard_pixels=0`, `key_dark_latch_rmt_writes=2`, `key_dark_latch_expiry_dirty=1`, `key_dark_clear_tx=spi_dma_prelatch_then_one_shot_rmt_gpio_low`, `key_lit_edge_tx=spi_dma_only`, `key_feedback_dynamic_tx=spi_dma_until_dark_latch`, `key_single_white_hold_ms=160`, `key_multi_key_independent_fade=1`, `strip_tx_failure_retry_dirty=1`, `suspended_strip_resume_dirty=1`, `low_power_final_latch_writes=3`, `rmt_idle_drive=active_dma_low_power_all_zone_non_dma_final_frame_then_release_gpio_low`, `low_power_transport_suspend_ms=0`, `status_tail_reinforce=recording_processing`, `status_tail_reinforce_writes=3`, `status_tail_overlap_reinforce_writes=1`, `status_tail_overlap_style=dma_audio_rec_ai_da_dada`, `recording_level_reactive=1`, `processing_thinking_style=single_then_double_beat`, `processing_thinking_color=purple_static`, `processing_thinking_scan_profile=da_long_gap_grouped_dada_rest`, `ota_progress_style=LED5_OK_cyan_pulse_EC11_progress_EDGE_chase`, `ota_progress_idle_blocker=POWER_MANAGER_BLOCKER_OTA`, `active_work_status_overlap_dynamic_1pct_eased=0`, `active_work_status_audio_reactive_rec=1`, `active_work_status_thinking_ai=1`, `strip_dirty_tx=1`, `status_tx_last=1`, and `dynamic_active_accents=1`. Historical brightness/cadence trials belong in validation artifacts, not this feature prose. If `detail=rgb` and `detail=rgb_ec11` show only the intended BLE/EC11 repair cue while a camera or eye sees other status windows flash during repair pulses, first check the RMT idle-drive/data-line behavior, then optical bleed, physical signal integrity, or mapping evidence before changing semantic rendering.
- Long-press shutdown confirmation: when EC11 long press crosses the power-control threshold, firmware shows a warm amber pending cue by restoring LED output, holding `PWR` amber, and filling the EC11 ring clockwise over 1.8 seconds; the edge/frame group stays off for this confirmation. After one full ring, the pending cue stays latched at full ring instead of timing itself out; only final long-press hardware shutdown, sleep, clear, or another explicit state transition turns it off. When hardware shutdown is actually confirmed, firmware shows a bright amber `PWR`-only cue and holds it until PWR_HOLD removes power or failure recovery restores the normal state, so automatic shutdown cannot look like every LED turned on or briefly black out before shutdown. The confirmation cue temporarily takes priority over REC/AI decorative accents, while `PWR`/`BLE` state remains independently rendered before the final cue.
- Warnings use `LED6=WARN` only. Retryable and hard error pulses do not borrow source LEDs, keys, EC11, or edge/frame accents, so an error is visually distinct from recording, processing, OK, and charging. Health-monitor BLE instability alerts are log-only and must not light `BLE` or `WARN` during idle; hard BLE failures and explicit BLE operation failures can still use the error path. Critical battery remains a dedicated `PWR` safety cue.
- The product palette favors clear semantic colors on the current diffuser: green for battery-good/OK, cyan-green for OTA progress, white for external power and detected physical key/EC11 press feedback, blue for BLE pairing, HID-only connected Type-search, and re-pair confirmation, gold for recording, red for hard warning, amber for lower battery or retryable warning, and purple for AI plus confirmed single/double/long key gestures.
- RGBW, map, chase, and pixel test commands remain calibration tools and can drive full brightness independent of the product profile.

- `~LED:PREVIEW disconnected`, `~LED:PREVIEW pairing`, `~LED:PREVIEW reconnect`, and `~LED:PREVIEW repairing` exercise the BLE connection states used for no-host active state, first pairing, host reconnect, and EC11 double-click re-pair recovery. Active disconnected/no-host keeps `LED2=BLE`, EC11, key, and edge-frame dark; it is a stable preview-only validation entry so `clear` can keep its source-of-truth resync behavior. Pairing keeps EC11 and edge/frame off, with `LED2=BLE` carrying the pairing cue through a visible dark off phase. Reconnect also uses a dark off phase. HID-only connected Type-search keeps a low-floor blue double-flash on `LED2=BLE`, making the low valley a connected-but-not-Type-ready marker. `repairing` should briefly report `ble_repair_ms_left>0`, keep `WARN` off unless a separate hard failure is injected, use synchronized `LED2=BLE` plus EC11 ring for the user-requested three-cycle double-flash confirmation, and keep key/edge-frame off.
- `~LED:PREVIEW recording_active` and `~LED:PREVIEW capture_active` are aliases for active device-mic capture, not effect-only previews: they must establish the connected ready baseline first, then add `LED3=REC` while keeping `LED1=PWR` and `LED2=BLE` independent.
- `~LED:PREVIEW recording_processing` shows the connected ready baseline plus active capture and host-processing: `LED1=PWR` and `LED2=BLE` remain independent, `LED3=REC` and `LED4=AI` are added, EC11/edge show low deterministic warm-gold same-cycle flow accents, key LEDs stay off unless physically pressed, and `LED5=OK`/`LED6=WARN` must remain off unless a later success or fresh error command is sent. Run `~LED:STATUS` during this preview and inspect the `detail=rgb` line to verify the current render-sampled status frame, not just a camera frame.
- `~LED:PREVIEW recording_processing_status_only` uses the same status `PWR/BLE/REC/AI` semantics while suppressing key, EC11, and edge accents. Use it only as a diagnostic split: if status-only still flashes physical LED5/LED6 while `detail=rgb` reports `OK=0,0,0;WARN=0,0,0`, the remaining issue is on the status rail itself rather than multi-zone accent interference.
- `~LED:PREVIEW ota` shows the product OTA scene with ordinary PWR/BLE baseline plus `LED5=OK`, EC11, and edge/frame OTA accents. `~LED:PREVIEW ota_led_only` shows only the OTA light surfaces for visual tuning. During either preview, `detail=state` should report `ota_active=1`, `processing=0`, and `ota_progress_percent=50`; `detail=summary active_flags` should include `OK`, `EC11`, and `EDGE`, and should not include `AI`.
- Dedicated LED-effect tuning must use `~LED:PREVIEW capture_led_only`, `~LED:PREVIEW recording_processing_led_only`, `~LED:PREVIEW recording_processing_status_led_only`, `~LED:PREVIEW processing_led_only`, `~LED:PREVIEW processing_status_led_only`, or `~LED:PREVIEW ota_led_only`. Full effect-only modes judge status, EC11, and edge together while the key strip stays off; status-only effect modes set `preview_suppress_accents=1` and keep key/EC11/edge off. Mutating `~LED:*` commands count as USB LED activity, and effect-only preview holds the USB-command power-manager blocker until `~LED:PREVIEW clear` or `~LED:OFF`, so low-power idle cannot clear the review state or hardware-shutdown the board while the human prompt is open. Power samples may still update diagnostic readback, but they do not reset the effect phase or change `last_reason` during effect-only review. Use ordinary `capture`, `recording_processing`, `processing`, and `ota` only for product-scene review where PWR/BLE participation is intentional.
- `~LED:PREVIEW recording_processing_status_key_stress` is a diagnostic-only repro pattern. It sets `preview_effect_only=1`, drives status `LED3=REC`/`LED4=AI` dynamically while keeping software `LED5=OK`/`LED6=WARN` at zero, and mirrors the status dynamics on the key strip without involving EC11 or edge LEDs. - `~LED:PREVIEW shutdown_confirm` and `~LED:PREVIEW shutdown_final` exercise the pending and final long-press shutdown confirmation effects without requiring an actual power-off. For pending shutdown review, wait longer than 1.8 seconds and confirm the EC11 ring remains fully lit until `shutdown_final`, `sleep`, `clear`, or a real power-off path clears it. For final shutdown review, confirm `PWR` is the only active LED and the EC11 ring is off; the final preview holds until `clear` or another preview state so review timing cannot expire it into a black frame.
- Runtime EC11 long-press pending shutdown feedback is canceled on EC11 release unless the power manager has already escalated to the final hardware-shutdown confirmation.

Real V2 hardware validation still has to record the actual RGB color order and physical LED order with photos or video. The firmware default color order is `GRB` for all four strips. Status/key use the 3528 WS2812-style part, while EC11/edge use the 4020 WS2812B part; both datasheets use 24-bit GRB data, but the 4020 part needs the longer reset latch and stricter low-time timing used by the backend.

During 2026-06-08 hardware bring-up, status/key LEDs responded on the current board but EC11/edge LEDs did not light after the firmware was flashed with the 4020-compatible timing above. Treat EC11/edge darkness as a separate hardware pinout or continuity investigation before changing firmware color order or WS2812 timing again.
