# Low-Power Hardware Shutdown Policy

Current V2/N16R8 firmware uses `components/power_manager` for runtime idle power reduction and long-idle hardware shutdown. The latest board revision maps `PWR_HOLD` to GPIO9 and `BAT_V_ADC` to GPIO10; the previous TPS63020/SY7088 current-sense chips are not populated. The long-idle path no longer uses ESP32-S3 Deep Sleep. Instead, configured long idle enters `POWER_MANAGER_STATE_HARDWARE_SHUTDOWN`, records diagnostics, prepares BLE/audio/LED shutdown, and actively drives `PWR_HOLD/GPIO9` HIGH through the board abstraction. `EC11-KEY_IO/GPIO18` is the power-on key while off, then a runtime custom-key/recovery input after boot; it is not the recording key. If boot starts while EC11/GPIO18 is already held, the runtime input suppresses that startup hold until stable release, so the power-on press cannot become a recording/custom-key/recovery action. The runtime EC11 single-click fallback is `Shift+F13`, not F25, so it stays within the supported host HID/hotkey contract without colliding with KEY1-KEY4 bare F13-F24 entries.

Observable firmware contract:

- `~POWER:STATUS` reports thresholds, blockers, `shutdown_blockers`, disabled GPIO7 diagnostics, USB SOF power, charger raw levels, interpreted `charger_active`, `charge_power_present`, `external_power_present`, `charging`, `charge_full`, audio-idle state, PWR_HOLD/GPIO9 status, and the cold-boot user action.
- Passive status queries used for power triage (`~POWER:STATUS`, `~BOARD:STATUS`, cached `~BOARD:POWER`, `~LED:STATUS`, and `~DEVICE:SETTINGS`/`STATUS`) do not refresh activity timers.
- Runtime low-power idle is user-configurable per power mode through persisted device settings. `~DEVICE:SET low_power_idle_ms=<0|60000..86400000>` or `~DEVICE:SET low_power_idle_minutes=<0..1440>` updates both modes; `0` disables low-power idle for that mode. `plugged_*` and `battery_*` keys update one mode. `~POWER:STATUS` reports effective and per-mode values.
- Plugged runtime low-power idle defaults to disabled so USB/charger attach stays responsive. `~DEVICE:SET plugged_low_power_enabled=<0|1>` controls whether external-power idle may enter connected/disconnected idle. Battery low-power idle remains enabled. BAT_CHG/GPIO14 and BAT_STD/GPIO21 are active-low wake inputs, armed only while battery idle.
- Automatic long-idle hardware shutdown has separate plugged and battery thresholds. Plugged auto-shutdown defaults to off; battery auto-shutdown defaults to 30 minutes. `~DEVICE:SET auto_shutdown_ms=<60000..86400000>` or `~DEVICE:SET auto_shutdown_minutes=off` updates battery mode; `plugged_auto_shutdown_ms|minutes` and `battery_auto_shutdown_ms|minutes` update one mode. Manual `~POWER:SHUTDOWN` and `~POWER:TEST:SHUTDOWN` remain explicit hardware-shutdown requests.
- GPIO7 USB_DET is disabled/high-Z and diagnostics-only. Computer USB is inferred from USB Serial/JTAG SOF together with exclusive charger VIN, so release defaults keep USB Serial/JTAG awake while connected (`CONFIG_USJ_NO_AUTO_LS_ON_CONNECTION=y`) to keep plugged detection, serial diagnostics, and flashing stable. The opt-in `sdkconfig.defaults.usb-light-sleep-debug` profile may be used only for bench experiments where Windows COM disconnects, missed console traffic, or unstable plugged detection are acceptable. Charger/external-power state comes from exclusive active-low `BAT_CHG` charging or exclusive active-low `BAT_STD` full/standby after debounce and a near-full battery guard. Both-high and both-low CHG/STD are no VIN, so PWR must not stay white after unplug. Unplugged reboot ignores the ESP-IDF assumed-connected SOF flag for 100 ms and holds charger pins at the unplugged-high default until 30 ms of agreeing samples, so a single boot-time `BAT_STD=0` cannot light PWR white.
- Active charging or charge-full status blocks this automatic low-battery shutdown. USB SOF also blocks low-battery shutdown.
- Battery percentage uses the product-protection range `2850mV=0%` and `4150mV=100%`; `2700mV` is an absolute danger marker. The GPIO10 68K/68K battery divider reconstructs VBAT from the ESP-IDF calibrated ADC pad voltage plus the NVS-persisted DMM trim set by `~BATTERY:CAL:DMM <mV>`, and `~BOARD:STATUS` / `~BATTERY:STATUS` report driver ADC pad mV, trim mV, final ADC pad mV, VBAT, and level for bench correlation. Battery-only operation at the default critical threshold `0%` forces hardware shutdown only after a valid `BAT_V_ADC/GPIO10` reading, continuous confirmation, and boot grace.
- BLE link churn is radio activity, not user activity. Once user/audio idle has elapsed and no non-external blocker is active, repeated BLE disconnect/reconnect or subscribe noise must preserve the current idle target instead of reopening high-power ACTIVE.
- OTA is a non-external active-work blocker. `firmware_ota_begin()` must set `POWER_MANAGER_BLOCKER_OTA`, and every finish, abort, verify failure, or set-boot failure path must clear it. While this blocker is present, `~POWER:STATUS blocker_names` / `awake_blocker_names` should include `ota`, and connected/disconnected low-power idle must not suspend LED transports, audio/power context, or the transfer path.
- Quiet ACTIVE is intentionally different from idle, and the BLE lamp distinguishes connected states: pairing and ordinary reconnecting are visible blue attention pulses with a dark off phase, HID-only BLE connected keeps a visible low blue floor while active, and `TYPE_READY` stays visible as steady blue. Active disconnected/no-host stays dark, so the low blue valley means a real BLE connection exists but Listener-Type is not ready yet. The audio transport keeps the strict 12 second Type heartbeat timeout for readiness, but the BLE LED holds Type-ready steady for 30 seconds after the last heartbeat while active so occasional host heartbeat jitter does not visually bounce the BLE lamp; explicit `TYPE:BYE`/`TYPE:STOP`, notify disable, or BLE disconnect still clears it immediately. Connected/disconnected idle clears active-work LEDs and decorative surfaces, keeps restrained PWR visible, and leaves reconnecting/connected/TYPE_READY BLE dark; routine Listener-Type heartbeat timeout/restore updates only semantic BLE state and must not reopen an active BLE window from idle. Pairing can still blink BLE as an attention state, and user-requested re-pair can still blink BLE plus the EC11 ring as the product confirmation cue; low-power reconnect stays dark so idle does not keep showing radio churn. Low-power idle and low-power resume send status clear/latch frames with the status strip forced to non-DMA, then immediately suspend the LED transports and drive their data GPIOs low so idle does not keep retransmitting status frames or relatch LED3-LED6.
- Runtime idle remains button-wakeable and knob-wakeable. KEY1-KEY4/GPIO38-GPIO41 keep active-low GPIO light-sleep wake enabled and use a 10 ms active scan with a 20 ms low-power scan, not runtime GPIO interrupts; EC11 push/GPIO18 keeps its ordinary edge IRQ plus active-low GPIO wake. EC11 A/B rotation must keep active GPIO edge IRQ plus a 20 ms low-power backup poll, and any valid low-power rotation edge records activity and restores the local white rotation cue before HID dispatch, so idle cannot swallow continuous knob movement. Continuous rotation feedback is maintained from valid encoder edges, but the ring head advances only on completed detents; partial edges refresh the visible cue and direction. Fixed-period auto-spin and per-edge multi-step are regressions because they make the cue faster than the physical knob. Fast rotation must compress duplicate raw ISR states, keep the latest overflow state, and chase the current physical A/B state after a burst so the cue does not freeze mid-turn. HID consumer backpressure during fast EC11 rotation is log-only and must not light `LED6=WARN`, because local knob feedback is the primary acknowledgement. Active-mode KEY1-KEY4 raw edges may show only an immediate local white preview; HID dispatch or purple gesture feedback still require a 20 ms elapsed-time debounce, including release-before-next-sample taps that have already held long enough, while sub-20 ms raw-only release must cancel the preview without leaving a release tail. Low-power KEY1-KEY4 edges must be confirmed before lighting or dispatching, and latched-but-released wake transients are ignored. EC11 push raw press edges only record activity during the double-click decision window so recovery cannot relatch stale accent strips before the synchronized BLE plus EC11 re-pair cue. Confirmed KEY gestures are purple; EC11 double-click recovery is the dedicated synchronized low-blue BLE plus EC11 re-pair cue. The EC11 push path must not switch to a low-level GPIO interrupt while idle, because a held or repeated press can turn the active-low level into an interrupt storm and trip the interrupt watchdog.
- EC11 fast-rotation support also depends on low-overhead background work: rotation feedback diagnostics are throttled, and the BLE HID usage queue is sized for short volume/brightness bursts so queue pressure cannot make the local ring cue expire while the knob is still moving.
- EC11 rotation has a longer low-tail hold than EC11 press feedback. The hold does not auto-spin the head; it only prevents the ring from going black across short slow-turn or scheduling gaps before the next valid encoder event or completed detent arrives. Interactive key/EC11 wake must cancel any pending black transition-clear frame so the first wake frame is the visible local feedback, not a whole-device off flash.
- Stable disconnected idle avoids routine 2s battery ADC reads and 2s power-manager polling. It reuses the cached battery snapshot between long refresh intervals and refreshes immediately when leaving disconnected idle or when USB/charger/external-power state changes. BLE remains connectable in this reversible idle state using low-duty 500--1000 ms advertising, so Listener-Type can reconnect without a key press; the 30--50 ms fast interval is restored only for ACTIVE/pairing work. Plugged soft-off and hardware shutdown still stop the radio and require the EC11 wake path.
- Unplugged/no-serial validation relies on flash-backed diagnostics after reconnect. `DIAG_LED_POWER_INPUT`, `DIAG_LED_VISUAL_STATE`, and `DIAG_LED_OUTPUT_STATE` persist LED-side power/charge/full flags, display-latched battery level, output-disabled/low-power transitions, active PWR/BLE/OK/WARN bits, and PWR RGB/color class.
- A successful shutdown request writes the final reason, idle time, blockers, battery snapshot, and power-source flags to NVS before driving `PWR_HOLD/GPIO9` HIGH, so the next boot can report the prior shutdown even if the serial log ended during power removal. Manual shutdown persists the soft-off guard for both plugged and battery operation. If an automatic battery/low-battery shutdown fails to remove power after the bounded observation window, firmware keeps `PWR_HOLD/GPIO9` HIGH, stops BLE advertising, enters key-wake-only quiescence, and reports `shutdown_failure_quiescent=1`; it does not restore runtime LOW or reconnect BLE on its own. A physical key activity or a power-source transition explicitly restores runtime LOW. Charging/USB automatic shutdown blocks also log `DIAG_POWER_EXTERNAL_POWER`, so exported diag logs can distinguish external-power policy from other blockers.

## Production Requirement

`PWR_HOLD/GPIO9` must remain actively driven LOW during normal boot and runtime. Configured long-idle or battery-only critical shutdown may drive it HIGH only after diagnostics, BLE disconnect preparation, I2S idle power-save, LED shutdown preparation, and a final blocker/power-source check.

Real confirmation that `PWR_HOLD/GPIO9` HIGH fully removes power, that short press cold-boots the device afterward, and that charging or charge-full state blocks automatic shutdown belongs to the hardware validation gate. Static firmware checks must not claim real power-off success.

The hardware gate must include decoded flash diag from the unplugged interval when reproducing behavior that happens away from USB serial. A PASS or root-cause claim for the USB-unplug light cycle must cite the decoded `status_led.power_input`, `status_led.visual_state`, `status_led.output_state`, `power.external_power`, and `power.sleep_wake` timelines, with event refs back to the raw diag log. The decoded bundle must pass `tools/verify_unplugged_flash_diag_bundle.py --expect-pwr-class amber --expect-pwr-class green` for the observed yellow/green PWR cycling case.

The policy is intentionally centralized in `power_manager` so desktop diagnostics and future board revisions can key off one stable status output instead of board-specific guesswork.

`~DEVICE:SETTINGS` reports the active and per-mode low-power idle timeouts, plugged low-power enable switch, active and per-mode shutdown timeouts, plugged/battery brightness caps, active power mode, and BLE name. `~POWER:STATUS low_power_idle_ms=... plugged_low_power_idle_ms=... battery_low_power_idle_ms=... plugged_low_power_enabled=... low_power_idle_allowed=... power_input_wake_configured=... power_input_irq_armed=... hardware_shutdown_ms=... plugged_auto_shutdown_ms=... battery_auto_shutdown_ms=...` reports the effective idle policy, power-input wake state, and timeouts that the power manager is currently using.

Use `tools/with_auto_shutdown_guard.ps1` around long validation or flash commands when the board is already running firmware. The tool reads `~DEVICE:SETTINGS`, temporarily sets the battery-only auto-shutdown timeout to the 24 hour firmware maximum, runs the guarded command, and restores the original value afterward. It cannot prevent USB ROM/stub transport loss during esptool flashing because that happens before the application firmware is running.
