# Low-Power Hardware Shutdown Policy

Current V2/N16R8 firmware uses `components/power_manager` for runtime idle power reduction and long-idle hardware shutdown. The long-idle path no longer uses ESP32-S3 Deep Sleep. Instead, battery-only long idle enters `POWER_MANAGER_STATE_HARDWARE_SHUTDOWN`, records diagnostics, prepares BLE/audio/LED shutdown, and drives `PWR_HOLD/GPIO11` HIGH through the board abstraction. `EC11-KEY_IO/GPIO18` is the power-on key while off, then a runtime custom-key/recovery input after boot; it is not the recording key. The runtime EC11 single-click fallback is `Shift+F13`, not F25, so it stays within the supported host HID/hotkey contract without colliding with KEY1-KEY4 bare F13-F24 entries.

Observable firmware contract:

- `~POWER:STATUS` reports thresholds, blockers, `shutdown_blockers`, USB/charger raw levels, interpreted `external_power_present`, `charging`, `charge_full`, current battery, `last_shutdown_*`, `audio_idle_power_save`, audio-idle blocker masking, `PWR_HOLD/GPIO11` status, `voice_key_gpio`, and the cold-boot user action.
- Passive status queries used for power triage (`~POWER:STATUS`, `~BOARD:STATUS`, `~LED:STATUS`, and `~DEVICE:SETTINGS`/`STATUS`) do not refresh activity timers, so they can be used to inspect idle state without waking the microphone path.
- Shutdown entry and rejected shutdown attempts log power diagnostics with blocker or reason fields. Charging/USB automatic shutdown blocks also log `DIAG_POWER_EXTERNAL_POWER`, so exported diag logs can distinguish external-power policy from other blockers.
- Automatic long-idle hardware shutdown keeps the 30 minute V2 default threshold (`CONFIG_POWER_MANAGER_HARDWARE_SHUTDOWN_MS=1800000`) but the runtime battery-mode threshold is user-configurable through persisted device settings: `~DEVICE:SET auto_shutdown_ms=<60000..86400000>` or `~DEVICE:SET auto_shutdown_minutes=<1..1440>`. The threshold applies only when battery powered. During normal boot/runtime the board actively drives `PWR_HOLD/GPIO11` LOW; only the shutdown path drives it HIGH. Hardware observation on 2026-06-11 confirms driving HIGH requests power-off, while runtime LOW keeps the external latch stable. No ESP sleep source is configured. If the board remains powered after a long-idle shutdown request, firmware keeps `PWR_HOLD/GPIO11` driven HIGH, feeds the watchdog, and suppresses BLE advertising restarts so the host does not see a reconnect loop while the device is supposed to be off.
- USB/VBUS detection blocks inactivity-triggered automatic hardware shutdown while preserving connected/disconnected awake idle behavior. External power does not keep the idle microphone/I2S path awake once the audio idle threshold is reached; `audio_idle_blockers` masks out the external-power blocker so plugged diagnostics can still prove whether audio capture has slept. Charger `CHG/STD` levels remain visible diagnostics, but they do not independently block battery-only long-idle shutdown after USB/VBUS is gone. The explicit `~POWER:SHUTDOWN` command remains the manual hardware-shutdown request and records `manual_command`.
- Battery percentage uses the product-protection range `3000mV=0%` and `4200mV=100%`; `2700mV` is treated only as an absolute danger marker, not as usable empty capacity. Battery-only operation at the default critical threshold `0%` forces hardware shutdown through the same `PWR_HOLD/GPIO11` drive-high path when the cell reaches product-empty, rather than shutting down early at a reserve percentage. USB/VBUS, active charging, or charge-full status blocks this automatic low-battery shutdown even if the battery estimate is critical.
- `CONFIG_PM_ENABLE`, `CONFIG_FREERTOS_USE_TICKLESS_IDLE`, and the connected/disconnected idle states remain the short-idle low-power behavior. They do not replace the long-idle hardware shutdown path.

## Production Requirement

`PWR_HOLD/GPIO11` must remain actively driven LOW during normal boot and runtime. Long-idle or battery-only critical shutdown may drive it HIGH only after diagnostics, BLE disconnect preparation, I2S idle power-save, LED shutdown preparation, and a final blocker/power-source check.

Real confirmation that `PWR_HOLD/GPIO11` HIGH fully removes power, that short press cold-boots the device afterward, and that USB/VBUS or charger-present state blocks automatic shutdown belongs to the hardware validation gate. Static firmware checks must not claim real power-off success.

The policy is intentionally centralized in `power_manager` so desktop diagnostics and future board revisions can key off one stable status output instead of board-specific guesswork.

`~DEVICE:SETTINGS` reports the battery-only timeout, plugged/battery brightness caps, active power mode, and BLE name. `~POWER:STATUS hardware_shutdown_ms=...` reports the effective timeout that the power manager is currently using.
