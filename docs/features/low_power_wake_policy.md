# Low-Power Hardware Shutdown Policy

Current V2/N16R8 firmware uses `components/power_manager` for runtime idle power reduction and long-idle hardware shutdown. The latest board revision maps `PWR_HOLD` to GPIO9 and `BAT_V_ADC` to GPIO10; the previous TPS63020/SY7088 current-sense chips are not populated. The long-idle path no longer uses ESP32-S3 Deep Sleep. Instead, battery-only long idle enters `POWER_MANAGER_STATE_HARDWARE_SHUTDOWN`, records diagnostics, prepares BLE/audio/LED shutdown, and actively drives `PWR_HOLD/GPIO9` HIGH through the board abstraction. `EC11-KEY_IO/GPIO18` is the power-on key while off, then a runtime custom-key/recovery input after boot; it is not the recording key. The runtime EC11 single-click fallback is `Shift+F13`, not F25, so it stays within the supported host HID/hotkey contract without colliding with KEY1-KEY4 bare F13-F24 entries.

Observable firmware contract:

- `~POWER:STATUS` reports thresholds, blockers, `shutdown_blockers`, USB/charger raw levels, interpreted `external_power_present`, `charging`, `charge_full`, current battery, `last_shutdown_*`, `audio_idle_power_save`, audio-idle blocker masking, `PWR_HOLD/GPIO9` status, `voice_key_gpio`, and the cold-boot user action.
- Passive status queries used for power triage (`~POWER:STATUS`, `~BOARD:STATUS`, cached `~BOARD:POWER`, `~LED:STATUS`, and `~DEVICE:SETTINGS`/`STATUS`) do not refresh activity timers, so they can be used to inspect idle state without waking the microphone path.
- Shutdown entry and rejected shutdown attempts log power diagnostics with blocker or reason fields. Charging/USB automatic shutdown blocks also log `DIAG_POWER_EXTERNAL_POWER`, so exported diag logs can distinguish external-power policy from other blockers.
- Runtime low-power idle defaults to 1 minute and is user-configurable through persisted device settings: `~DEVICE:SET low_power_idle_ms=<60000..86400000>` or `~DEVICE:SET low_power_idle_minutes=<1..1440>`. The threshold applies to both connected and disconnected idle, and `~POWER:STATUS low_power_idle_ms=... connected_idle_ms=... disconnected_idle_ms=...` reports the effective value.
- Plugged runtime low-power idle defaults to enabled so upgraded devices preserve existing USB/VBUS idle current behavior. `~DEVICE:SET plugged_low_power_enabled=<0|1>` controls whether external-power idle may enter `CONNECTED_IDLE`/`DISCONNECTED_IDLE`; when disabled while USB/VBUS is present, `~POWER:STATUS plugged_low_power_enabled=0 low_power_idle_allowed=0` stays in `ACTIVE` instead of the runtime low-power states. Battery low-power idle and battery-only automatic shutdown remain enabled by their own thresholds.
- Automatic long-idle hardware shutdown keeps the 30 minute V2 default threshold (`CONFIG_POWER_MANAGER_HARDWARE_SHUTDOWN_MS=1800000`) but the runtime battery-mode threshold is user-configurable through persisted device settings: `~DEVICE:SET auto_shutdown_ms=<60000..86400000>` or `~DEVICE:SET auto_shutdown_minutes=<1..1440>`. The threshold applies only when battery powered. During normal boot/runtime the board actively drives `PWR_HOLD/GPIO9` LOW; only the shutdown path keeps the GPIO in output mode, drives it HIGH, and waits up to 500 ms for readback before observing power removal. Hardware logs on 2026-06-15 showed the previous input/high-Z release path stayed LOW, so firmware now uses an explicit drive-HIGH request. No ESP sleep source is configured. Firmware treats failed `PWR_HOLD/GPIO9` readback as a hard shutdown failure; if the board is still powered after the bounded power-removal observation window, it restores runtime LOW, requests BLE reconnect, records `DIAG_POWER_SLEEP_BLOCKED`, and resets idle timers instead of staying in a silent wait state.
- USB/VBUS detection blocks inactivity-triggered automatic hardware shutdown while preserving connected/disconnected low-power idle behavior only when `plugged_low_power_enabled=1`. External power does not keep the idle microphone/I2S path awake once the audio idle threshold is reached; `audio_idle_blockers` masks out the external-power blocker so plugged diagnostics can still prove whether audio capture has slept. Charger `CHG/STD` levels remain visible diagnostics, but they do not independently block battery-only long-idle shutdown after USB/VBUS is gone. The explicit `~POWER:SHUTDOWN` command remains the manual hardware-shutdown request and records `manual_command`.
- BLE link churn is radio activity, not user activity. Once the user/audio idle threshold has elapsed and no non-external blocker is active, repeated BLE disconnect/reconnect or subscribe noise must preserve the current idle target instead of reopening a high-power ACTIVE window.
- Disconnected idle is key-wake-only: firmware stops connectable BLE advertising after the low-power idle threshold, keeps audio/status LEDs in idle power save, and waits for a physical key/custom-key/recovery action to reopen the fast 30-50ms advertising window. This removes BLE auto-wake/reconnect RF pulses from steady idle; recovery pairing commands still explicitly reopen advertising for rediscovery.
- Stable disconnected idle also avoids routine 2s battery ADC reads and 2s power-manager polling after the low-power state is reached. It reuses the cached battery snapshot between long refresh intervals, refreshes immediately when leaving disconnected idle or when USB/external-power state changes, and lets `~POWER:STATUS` report the cached idle battery value without forcing an ADC burst. `~BOARD:POWER` keeps the optional current-rail diagnostic rows for parser compatibility, but the current board must report both rails as `present=0 gpio=-1 current_model="not_populated"`; GPIO9 and GPIO10 must not be reused as current telemetry. The idle monitor defaults to status-only polling.
- Battery percentage uses the product-protection range `2800mV=0%` and `4200mV=100%`; `2700mV` is treated only as an absolute danger marker, not as usable empty capacity. Battery-only operation at the default critical threshold `0%` forces hardware shutdown through the same `PWR_HOLD/GPIO9` drive-high path only after a valid battery reading from `BAT_V_ADC/GPIO10` confirms `<=2800mV`, the continuous low-battery confirmation window passes, and the short boot grace window has elapsed, so ADC/USB_DET startup transients cannot immediately power the board off. USB/VBUS, active charging, or charge-full status blocks this automatic low-battery shutdown even if the battery estimate is critical.
- `CONFIG_PM_ENABLE`, `CONFIG_FREERTOS_USE_TICKLESS_IDLE`, and the connected/disconnected idle states remain the short-idle low-power behavior. Connected/disconnected idle also disables routine status LED output and leaves only event-driven wake feedback, while the status LED task suppresses unchanged-frame writes and uses a slower static-idle cadence. These runtime idle reductions do not replace the long-idle hardware shutdown path.
- Unplugged/no-serial low-power validation must rely on flash-backed diagnostics after reconnect, not on live serial. `DIAG_LED_POWER_INPUT`, `DIAG_LED_VISUAL_STATE`, and `DIAG_LED_OUTPUT_STATE` persist LED-side power/charge/full flags, raw/display-latched battery level, suppressed battery-only display rises, output-disabled/low-power transitions, active PWR/BLE/OK/WARN bits, and PWR RGB/color class so observations such as "status LEDs went dark, later resumed, and the PWR LED alternated amber/green" can be reconstructed from `tools/dump_diag_log.ps1` + `tools/decode_diag_log.py` after the device is plugged back in or cold-booted.
- If PWR_HOLD/GPIO9 fails to remove power during automatic battery-only shutdown, firmware restores runtime LOW, records the failure and a bounded retry cooldown in flash diagnostics, and stays in low-power LED-off behavior instead of immediately reopening BLE reconnect. Manual `~POWER:SHUTDOWN` failures still restore interactivity for debugging.

## Production Requirement

`PWR_HOLD/GPIO9` must remain actively driven LOW during normal boot and runtime. Long-idle or battery-only critical shutdown may drive it HIGH only after diagnostics, BLE disconnect preparation, I2S idle power-save, LED shutdown preparation, and a final blocker/power-source check.

Real confirmation that `PWR_HOLD/GPIO9` HIGH fully removes power, that short press cold-boots the device afterward, and that USB/VBUS or charger-present state blocks automatic shutdown belongs to the hardware validation gate. Static firmware checks must not claim real power-off success.

The hardware gate must include decoded flash diag from the unplugged interval when reproducing behavior that happens away from USB serial. A PASS or root-cause claim for the USB-unplug light cycle must cite the decoded `status_led.power_input`, `status_led.visual_state`, `status_led.output_state`, `power.external_power`, and `power.sleep_wake` timelines, with event refs back to the raw diag log. The decoded bundle must pass `tools/verify_unplugged_flash_diag_bundle.py --expect-pwr-class amber --expect-pwr-class green` for the observed yellow/green PWR cycling case.

The policy is intentionally centralized in `power_manager` so desktop diagnostics and future board revisions can key off one stable status output instead of board-specific guesswork.

`~DEVICE:SETTINGS` reports the low-power idle timeout, plugged low-power enable switch, battery-only shutdown timeout, plugged/battery brightness caps, active power mode, and BLE name. `~POWER:STATUS low_power_idle_ms=... plugged_low_power_enabled=... low_power_idle_allowed=... hardware_shutdown_ms=...` reports the effective idle policy and timeouts that the power manager is currently using.
