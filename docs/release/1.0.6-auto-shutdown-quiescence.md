# 1.0.6 candidate: automatic shutdown quiescence

## Problem addressed

On a V2 board, battery auto-shutdown requests hardware power removal by driving
`PWR_HOLD/GPIO9` HIGH. If the external latch does not remove the rail inside the
bounded observation window, the previous recovery path drove GPIO9 LOW again
and returned to normal BLE/runtime behavior. That recovery could look like the
device had shut down and then powered itself back on.

## New firmware contract

- Manual shutdown failure remains recoverable: runtime LOW and the normal
  reconnect path are restored.
- Automatic long-idle and low-battery shutdown failure now stays
  `key-wake-only` and keeps the shutdown request HIGH. BLE advertising is
  stopped and the state is exposed as `shutdown_failure_quiescent=1` in
  `~POWER:STATUS`.
- A physical key activity or a power-source transition is the explicit recovery
  boundary. That boundary restores runtime LOW before normal BLE/audio state is
  resumed.
- The failure is still retained in the diagnostic log and NVS shutdown trace;
  the code does not wait indefinitely or silently feed the watchdog.

## Verification

- `python tools/verify_power_manager_static.py` — PASS
- `pwsh tools/build.ps1` — PASS (`voice-keyboard-firmware.bin`, ESP32-S3)

Physical acceptance still requires flashing the resulting OTA package, setting
a short battery-only auto-shutdown timeout, unplugging USB, and confirming that
the device remains off/quiescent until an intentional key wake. A powered rail
with `shutdown_failure_quiescent=1` is a hardware-latch failure to investigate,
not a firmware permission to reconnect automatically.
