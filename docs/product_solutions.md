# 产品方案

## 1. 当前原则

这份文档只写当前阶段的产品方案建议。

当前前提是：

- 公司初期先以 `ESP` 为主
- 开发流程保留 `STM32` 落位
- 如果后续产品需求变化，可以单独切换某条产品线

协议相关当前约定是：

- `后端` 主导协议定义
- `嵌软` 配合协议落地与联调
- 正式协议文档由后端维护
- 项目开始前必须先冻结协议

即使正式协议由后端主导，项目开始前也必须冻结下面这些内容：

- 设备到后端的传输路径
- 控制消息格式
- 音频上传格式
- 请求响应结构
- 错误码规则
- 协议版本规则
- 超时与重试规则

尤其要尽快定清楚音频相关内容：

- 编码格式
- 采样率
- 位宽
- 声道数
- 分包方式
- 结束标记
- 超时规则

正式协议文档里，建议至少包含下面这些身份字段：

- `device_id`
- `hw_rev`
- `fw_version`
- `protocol_version`
- `partition_version`
- `build_id`

当前原则是：

- `传输层` 和 `业务协议` 分开设计
- 协议变更必须有版本号
- 协议变更必须带示例报文
- 协议变更必须带错误码表
- 协议变更最好带回放脚本
- 后端改协议时必须同步嵌软
- 音频格式不能只口头约定

## 2. 蓝牙语音键盘

### 2.1 当前建议

首发方案建议先用：

- `ESP32-C3`

推荐 Flash 容量先定为：

- `4 MB`

推荐优先模组：

- `ESP32-C3-MINI-1-N4`

当前这样选，主要是为了先控成本。

### 2.2 当前这样定的原因

- 第一版重点是先把 `BLE 键盘 + 语音输入` 跑通
- `ESP32-C3` 更适合当前公司的命令行开发和 `Codex` 协作方式
- USB、日志、烧录、调试链路更容易先统一
- 可以更快接到后端，把语音输入闭环做出来

从成本看，按 `2026-05-11` 查到的 `LCSC` 价格：

- `ESP32-C3-MINI-1-N4`：`$2.2254 @100+`，`$2.0964 @1300+`

对键盘这条线来说，第一版先用 `4 MB` 更合适：

- 成本最低
- 第一版功能仍有机会做最小 OTA 预留
- 只要控制 app 体积，`4 MB` 依然可以做双分区 OTA 思路

### 2.3 第一版建议能力范围

第一版优先做：

- BLE HID 键盘
- 按键扫描
- 语音键触发录音
- 音频采集
- 音频上传
- 返回文本后的输入注入
- 日志、自检

键盘 `v1` 的无线范围当前直接锁定为：

- `BLE only`
- `Wi-Fi` 默认关闭
- `2.4G dongle` 不在 `v1`

第一版先不强求：

- 极致低功耗
- 极致薄型化
- 极致键盘手感优化
- 自定义 `2.4G USB 接收器`
- 完整 OTA 闭环

### 2.4 键盘音频传输策略

键盘 `v1` 不按“音频文件上传/下载”来做，
而按“短句语音流式传输”来做。

当前建议直接锁定为：

- 上行：`BLE` 小分片流式上传
- 下行：先只回文本结果
- `v1` 不回音频文件

这样定的原因是：

- 传完整音频文件，延迟会明显变大
- `BLE` 更适合短分片连续传输
- 键盘的核心目标是语音转文字输入，不是语音播放
- 先不接收音频文件，可以明显降低复杂度、功耗和时延

建议的上行方式是：

- 按住语音键后开始采集
- 边采边通过 `BLE` 连续上传
- 不等整段录完再传
- 音频内容按固定小分片发送

首版建议先按下面这个量级评估：

- `mono`
- `16 kHz`
- `16-bit PCM`
- `20~40 ms` 一片

如果后端和中转端配合得好，建议：

- 后端收到分片就开始处理
- 先回部分结果
- 最后回最终文本

当前不建议：

- 先录完整段 `wav` 再上传
- 用 `base64` 把音频塞进大 JSON
- 在键盘 `v1` 上接收和播放音频文件

### 2.5 OTA 预留原则

键盘第一版可以先不做完整 OTA，但建议一开始就预留升级路径。

建议现在就做的准备：

- 预留足够的 Flash 容量
- 分区表或固件布局预留双镜像升级空间
- 启动流程预留版本校验、回滚或升级状态位
- 配置存储里预留升级相关字段

建议现在先不要做的部分：

- OTA 服务端
- 完整升级 UI
- 很复杂的升级策略
- 独立自研 bootloader

对当前阶段来说，更合适的是：

- 先用官方或平台默认 bootloader 方案
- 先把升级所需的分区、状态位和回滚思路留出来
- 等产品闭环稳定后，再补完整 OTA

键盘这条线当前建议是：

- `先按 4 MB 做`
- `先预留 OTA 分区思路`
- `先不为 OTA 提前上更大 Flash`
- `v1 硬件只预留 OTA 结构，不承诺首批量产启用 OTA`

关于 `2.4G` 预留，当前建议是：

- `软件先不做 2.4G`
- `硬件先不为 2.4G dongle 单独加额外接口`
- `板级布局尽量给后续天线、测试点和器件调整留空间`

也就是说：

- 当前不用为了未来 `2.4G dongle`，先把接口和复杂度堆上去
- 但 PCB 和结构不要把后续无线调整空间完全锁死

如果后面出现下面情况，再升级到更大 Flash 模组：

- 固件体积明显长大
- 2.4G dongle、更多协议或更多本地功能进入量产版本
- OTA 需要更大的回滚空间
- 需要更多本地资源或诊断信息

后续如果要升级容量，优先路径是：

- `换更大 Flash 的模组`

不建议优先走：

- `外挂 Flash 作为主 OTA 固件存储`

### 2.6 后续什么情况下考虑切到 STM32

如果后面蓝牙键盘更强调下面这些目标，可以考虑从 `ESP` 切到 `STM32`：

- 更低功耗
- 更强的 BLE 键盘体验
- 更强的外设实时控制
- `2.4G dongle` 变成刚需
- 设备形态变得更像传统无线键盘，而不是语音输入设备

### 2.7 迁移原则

如果后面切到 `STM32`，原则是：

- `app/`
- `services/`
- `protocols/`

尽量不大改。

主要新增或替换：

- `ports/stm32/`
- `boards/keyboard_stm32/`
- 构建与调试脚本

## 3. 随身听 / 听力类设备

### 3.1 当前建议

首发方案建议先用：

- `ESP32-S3`

这条线当前按 `日常使用的音频/语音设备` 定义，
不按 `医疗级助听器` 标准定义。

推荐 Flash 容量先定为：

- `8 MB` 作为最低建议
- `16 MB` 作为更推荐方案

如果体积允许，推荐优先模组：

- `ESP32-S3-WROOM-1-N16R8`

如果更在意尺寸，备选：

- `ESP32-S3-MINI-1-N8`

### 3.2 当前这样定的原因

- 这条产品线更偏 `音频 + 语音 + 联网`
- `ESP32-S3` 更适合先做录音、上传、播放、回复闭环
- 原生 USB、日志和 JTAG 调试方式对开发更友好
- 更适合 `Codex` 用命令行完成编译、烧录、读日志、分析和调试

从成本看，按 `2026-05-11` 查到的 `LCSC` 价格：

- `ESP32-S3-MINI-1-N8`：`$3.5495 @100+`，`$3.3120 @1300+`
- `ESP32-S3-WROOM-1-N8R8`：`$3.6256 @100+`，`$3.4044 @1300+`
- `ESP32-S3-WROOM-1-N16R8`：`$3.4836 @100+`，`$3.2668 @1300+`

所以对随身听这条线来说：

- `8 MB` 是最低建议
- `16 MB` 更稳，而且当前价格差并不大
- 如果体积允许，`N16R8` 的性价比反而很好

### 3.3 第一版建议能力范围

第一版优先做：

- 麦克风采集
- 音频上传
- 后端返回文本和语音结果
- 本地播放
- 基础按键或简单交互
- 状态管理
- 日志、自检

第一版先不强求：

- 很复杂的本地 UI
- 很强的离线智能
- 很极致的低功耗优化
- 很重的多媒体能力
- 完整 OTA 闭环

### 3.4 OTA 预留原则

随身听第一版也可以先不做完整 OTA，但建议从一开始就预留升级路径。

建议现在就做的准备：

- 预留足够的 Flash 容量
- 分区表或固件布局预留双镜像升级空间
- 启动流程预留版本校验、回滚或升级状态位
- 设备协议里预留版本与升级状态字段

建议现在先不要做的部分：

- 完整 OTA 服务流程
- 很复杂的升级策略
- 升级失败的多轮恢复机制
- 独立自研 bootloader

对当前阶段来说，更合适的是：

- 先用官方或平台默认 bootloader 方案
- 先把升级边界和存储布局定好
- 等录音、上传、播放闭环稳定后，再补完整 OTA

随身听这条线当前建议是：

- `不要按 4 MB 做`
- `至少按 8 MB 做`
- `如果体积和成本能接受，优先 16 MB`

原因是这条线后面更容易吃掉 Flash：

- OTA 双分区
- 音频链路相关功能增长
- 日志和诊断信息增长
- 本地资源、配置和缓存增长

### 3.5 后续是否考虑切到 STM32

当前不建议优先考虑切到 `STM32`。

原因是：

- 这条线长期更可能持续依赖音频和语音能力
- `ESP32-S3` 与当前需求更贴近
- 统一在 `ESP` 上更有利于前期快速迭代

只有在下面情况明显出现时，再重新评估：

- 功耗约束突然变得非常强
- 外设控制比联网和语音更重要
- 产品定位发生明显变化

## 4. 当前拍板

公司当前建议这样落地：

- `蓝牙语音键盘`：首发先用 `ESP32-C3`
- `随身听 / 听力类设备`：首发先用 `ESP32-S3`
- 公司初期统一主平台：`ESP`
- 公司流程同时保留 `STM32` 落位
- `蓝牙语音键盘 v1`：只预留 OTA 结构，不承诺首批量产启用 OTA

一句话：

`先用 ESP 把两条产品线跑起来；以后如果键盘对低功耗、BLE 或 2.4G 有更强要求，再单独切 STM32。`
