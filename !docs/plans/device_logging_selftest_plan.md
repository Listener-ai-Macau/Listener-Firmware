# 设备日志与自检方案

## 目标

为蓝牙语音键盘建立统一的日志、自检和故障定位能力，降低后续 AI 与人工联调成本。

## 问题

当前仓库虽然已经有部分运行日志，但还没有形成统一的设备诊断能力：

- 启动阶段缺少统一自检清单
- 缺少统一的模块状态标记
- 缺少“键输入 / 语音键 / 音频 / BLE / 文本注入”全链路统一诊断视角

## 范围

- 启动自检清单
- 关键模块状态日志
- 版本与构建信息输出
- 运行时错误分类
- 最小化回归验证入口

## 不在本次范围内

- 云端日志平台
- 复杂 crash dump 分析系统
- 量产测试工站软件

## 前提与依赖

- 当前仓库会持续增加多个子系统
- 需要在功能逐步落地前先把诊断思路定清楚

## 步骤

### 第一步：定义统一诊断面

状态：`pending`

工作内容：

- 明确哪些模块必须暴露状态
- 明确最小日志集合

验收方式：

- 文档中明确列出统一诊断面

人工检查点：

- 人确认诊断面可接受后，AI 才进入第二步

### 第二步：定义启动自检与运行时标记

状态：`pending`

工作内容：

- 明确启动时必须检查哪些模块
- 明确运行时关键日志标记

验收方式：

- 文档中明确写出自检项和关键日志标记

人工检查点：

- 人确认自检和日志标记可接受后，AI 才进入第三步

### 第三步：定义最小回归验证入口

状态：`pending`

工作内容：

- 明确后续 AI 应如何快速判断设备当前在哪一层出问题

验收方式：

- 文档中明确写出最小回归与定位入口

人工检查点：

- 人确认日志与自检方案可接受后，AI 才进入实现

## 当前阻塞项

- 需要先统一对未来模块的诊断要求

## 备注

- 该方案对所有后续功能都起支撑作用
- 越早收掉，后续 AI 联调效率越高
