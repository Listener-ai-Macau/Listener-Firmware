# 音频输入输出与主机侧保存验证方案

## 目标

基于当前 `ESP32-S3` 开发板原理图和本机官方示例，明确这块板子的：

- 语音输入链路怎么走
- 语音输出链路怎么走
- 在没有后端时，怎样先验证“麦克风采样真的打通了”

本方案当前优先达成的最小闭环不是“语音识别”，而是：

1. 设备采到麦克风音频
2. 把原始音频保存到电脑端
3. 能用最小客观方法判断录音是否正常
4. 设备能播放一段测试音频，先以中文“测试”为目标

## 当前问题

当前仓库已经有：

- `BLE HID` 键盘链路
- 串口日志抓取脚本
- 串口发送脚本

但当前还没有：

- 音频输入驱动
- 音频输出驱动
- 主机侧接收和保存 PCM/WAV 的脚本
- 一套不依赖后端的音频输入验收方法

## 范围

- 明确板级音频输入路径
- 明确板级音频输出路径
- 明确建议的 I2C / I2S 引脚映射结论
- 定义“设备录音并保存到电脑端”的最小验证方案
- 定义“播放中文测试音频”的最小验证方案

## 不在本次范围内

- 语音识别
- 云端上传
- 文本理解
- 产品级降噪、AEC、VAD 优化
- 最终音频协议冻结

## 当前结论

### 一、语音输入怎么走

当前原理图和本机示例基本支持下面这条链路：

`MIC -> ES8311 ADC -> I2S -> ESP32-S3`

更具体地说：

- 板上模拟麦克风器件是 `XF2718T09`
- 麦克风差分信号为 `MIC_P / MIC_N`
- `MIC_P / MIC_N` 进入 `ES8311`
- `ES8311` 负责把模拟信号转成数字音频
- `ESP32-S3` 通过 `I2S` 从 `ES8311` 读取数字音频

### 二、语音输出怎么走

当前原理图和本机示例基本支持下面这条链路：

`ESP32-S3 -> I2S -> ES8311 DAC -> NS4150B PA -> Speaker / 耳机座`

更具体地说：

- `ESP32-S3` 通过 `I2S` 把数字音频送给 `ES8311`
- `ES8311` 做数模转换，输出 `OUTP / OUTN`
- `OUTP / OUTN` 进入 `NS4150B`
- `NS4150B` 放大后输出到喇叭
- 同时原理图还有一个 `PJ-322` 音频座

### 三、当前最可信的板级引脚映射

从原理图页 1 和页 2，结合本机 `01_audio_es8311` 示例，当前最可信的结论是：

- `ES8311 I2C`：
  - `SDA1 -> GPIO4`
  - `SCL1 -> GPIO5`
- `ES8311 I2S`：
  - `I2S_BCLK / I2S_SCLK -> GPIO39`
  - `I2S_DIN -> GPIO40`
    这里是 `ESP32-S3` 接收录音数据
  - `I2S_WS / I2S_LRCK -> GPIO41`
  - `I2S_DOUT / I2S_ASDOUT -> GPIO42`
    这里是 `ESP32-S3` 发播放数据
  - `I2S_MCLK -> GPIO45`

这个结论和本机官方示例 `01_audio_es8311/main/main.c` 完全一致。

### 四、喇叭使能不是自动的

本机示例表明，想让扬声器真正出声，除了初始化 `ES8311`，通常还要额外拉高板上的扩展 IO：

- 通过 `XL9555`
- 控制 `MUTE` 引脚
- 示例中是 `P1.7`

所以播放链路验证不能只写 `ES8311 + I2S`，还要把 `XL9555` 控制考虑进去。

## 核心判断

### 判断 1：没有后端时，最好的输入验证不是“阈值触发字符串”

如果只是做“有声音就触发固定字符串”，它只能证明：

- 麦克风大概有活动

但它不能客观回答：

- 采样有没有削顶
- 噪声是不是过大
- 实际音色是否可用
- 左右声道或格式有没有错位

因此如果你现在最关心的是“语音输入到底好不好”，当前最优先的最小闭环应该改成：

`设备录音 -> 电脑端保存为 WAV -> 人直接试听 + 看波形`

### 判断 2：没有后端时，主机端保存 WAV 是最稳的验收方式

原因是：

- 你可以直接听
- 可以导入 `Audacity`
- 可以看波形、静音底噪、爆音、削顶
- 出问题时比单纯日志更容易判断是硬件、增益还是格式问题

### 判断 3：输出验证先不要走 TTS

你提到“说一句中文‘测试’就好了”，当前最稳的做法不是上 TTS，而是：

- 先准备一段主机侧固定 PCM / WAV
- 内容就是中文“测试”
- 用脚本把它送到设备
- 设备播出来

这样能把问题边界控制住：

- 只验证“播放通路”
- 不把 `TTS`、编码、后端一起掺进来

## 推荐方案

### 第一部分：输入验证方案

建议做成：

1. 固件初始化 `ES8311 + I2S`
2. 固件采集固定时长 PCM
3. 固件通过串口把 PCM 流输出到主机
4. 主机脚本保存为 `wav`
5. 主机侧执行基础检查：
   - 文件长度正确
   - 采样率正确
   - 峰值不是全零
   - 峰值没有长期顶满
6. 人工试听

主机侧保存格式建议：

- `mono`
- `16 kHz`
- `16-bit PCM`
- `wav`

建议录音时长：

- `3 ~ 5 秒`

为什么不建议第一步就直接 BLE 传音频：

- 当前仓库没有自定义 BLE 音频通道
- 串口直出更容易调试
- 主机脚本实现成本更低
- 先证明板上采样真的好，再讨论无线传输

### 第二部分：输出验证方案

建议做成：

1. 主机提前准备一个短 `wav`
2. 内容为中文“测试”
3. 脚本把 `wav` 转成设备期望的 `16k/16bit/mono PCM`
4. 通过串口发送到设备
5. 设备缓存后播放
6. 人工确认喇叭是否正常出声

如果当前输出实现想更简单，也可以先不做“主机传音频”，而是：

- 直接把一小段“测试”的 PCM 编进固件
- 上电播放一次

但从长期看，更推荐“主机脚本下发 PCM”的方式，因为后面更容易扩展成：

- 回放任意测试样本
- 做回环测试
- 做频响或失真排查

## 步骤

### 第一步：冻结音频输入输出引脚映射结论

状态：`pending`

工作内容：

- 以当前文档中的映射结论作为仓库默认方案
- 如果后续实测发现不符，再修订本方案

验收方式：

- 人确认当前引脚结论可接受：
  - `I2C SDA=GPIO4`
  - `I2C SCL=GPIO5`
  - `MCLK=GPIO45`
  - `BCLK=GPIO39`
  - `WS=GPIO41`
  - `I2S DIN=GPIO40`
  - `I2S DOUT=GPIO42`

人工检查点：

- 人确认后，AI 才进入第二步实现方案细化或代码实现

### 第二步：建立“设备录音 -> 主机保存 WAV”方案

状态：`pending`

工作内容：

- 在仓库里定义：
  - 固件采样接口
  - 串口导出格式
  - 主机侧保存脚本
- 尽量让主机脚本自动生成 `.wav`

验收方式：

- 文档中明确写出：
  - 串口导出协议
  - WAV 保存格式
  - 采样时长
  - 成功标志

人工检查点：

- 人确认这就是当前优先验证路径，AI 才进入实现

### 第三步：建立“播放中文‘测试’”的最小验证方案

状态：`pending`

工作内容：

- 明确输出验证走哪条路：
  - 固件内置 PCM
  - 或主机脚本下发 PCM
- 明确需要启用 `XL9555 MUTE`

验收方式：

- 文档中明确写出：
  - 音频来源
  - PCM 格式
  - 是否依赖 `XL9555`
  - 成功标志

人工检查点：

- 人确认输出验证路径后，AI 才进入实现

### 第四步：把当前占位输入方案和正式采音方案重新分工

状态：`pending`

工作内容：

- 明确：
  - `audio_input_placeholder_plan` 负责“音频活动带动整机交互”
  - 本方案负责“音频质量可观测性”

验收方式：

- 两份文档职责边界清晰，不互相打架

人工检查点：

- 人确认方案拆分合理后，AI 再继续下一步

## 当前阻塞项

- 当前仓库还没有 `esp_codec_dev / es8311 / xl9555` 相关依赖和驱动落地
- 还没有主机侧保存 `wav` 的脚本
- 还没有统一的串口音频导出协议

## 备注

当前建议的优先级是：

1. 先做“录音保存到电脑端”
2. 再做“中文‘测试’播放”
3. 最后再回到“语音活动触发固定字符串”这类占位交互

原因是：

`先听到真实录音、看到真实波形，才能客观判断麦克风链路是不是好；否则太容易在还没拿到干净音频之前，就把精力花在后面的交互流程上。`
