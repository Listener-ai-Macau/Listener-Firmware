# 类闪电说嵌入式语音助手总体方案

## 目标

明确 `voice-keyboard-firmware` 的最终形态如果要做成“类似 `shandianshuo.cn`，但触发入口和硬件形态是嵌入式设备”时，整体系统应该怎么拆、当前这个固件仓库应该负责哪一层，以及接下来应先做什么。

这里的“类似闪电说”，当前按 `2026-05-13` 首页公开能力理解为：

- 语音输入
- 长按唤醒
- 上下文理解
- 自动填入结果
- 自定义技能
- 本地与云端模型可切换

参考来源：

- https://shandianshuo.cn/

## 当前问题

当前仓库已经打通的是：

- `ESP32-S3` 开发板
- `BLE HID` 键盘连接与自动回连
- 固件侧字符注入到 `Windows`

但这离“类似闪电说”的最终产品还差了几个关键层次：

- 当前仓库只有固件，没有主机伴随程序
- 当前 `BLE HID` 路径本质上是按键码输入，不是完整的 Unicode 文本注入方案
- 当前设备还看不到屏幕内容，也没有个人记忆和技能执行层
- 当前没有音频流协议、没有主机侧或后端侧识别闭环

所以如果目标真的是“像闪电说”，那最终系统一定不是“只有一个 BLE 键盘固件”这么简单，而应该是：

- `嵌入式设备`
- `主机伴随程序`
- `AI / 后端服务`

三层协同。

## 范围

- 定义最终目标能力的系统拆分
- 明确当前固件仓库负责的边界
- 明确为什么“纯 BLE HID”不足以承载最终目标
- 给出分阶段落地顺序
- 让现有 `v1` 设备侧 roadmap 与最终目标之间建立清晰关系

## 不在本次范围内

- 直接开始实现主机伴随程序
- 直接开始实现后端
- 冻结正式协议字段细节
- 决定最终商业化计费、账号体系或运营策略
- 完成所有技能设计

## 前提与依赖

- 当前产品边界基线仍以 [product_solutions.md](../product_solutions.md) 为准
- 当前板级音频入口已确认是：
  `MIC -> ES8311 -> I2S -> ESP32-S3`
- 当前主机验证环境以 `Windows` 为主
- 当前 `BLE HID` 已经可作为“最小输入回路”保底链路
- 当前如果要实现“像闪电说”的中文输入、上下文理解、技能执行，必须引入主机侧能力

## 核心判断

### 1. 最终产品不应该只靠标准 BLE 键盘协议

如果只保留“标准 BLE 键盘”这一条链路，最终会卡在这些地方：

- 很难稳定做中文和任意 Unicode 文本注入
- 很难做“选中文本后改写”
- 很难做“读屏理解上下文”
- 很难做“执行技能后自动把结果填回当前应用”

因此最终建议是：

- `BLE HID` 保留为兼容层和保底输入层
- 真正的“语音助手能力”走主机伴随程序

### 2. 最合理的系统结构是“三层架构”

#### 设备层

负责：

- 语音键 / 物理交互
- 麦克风采集
- 基础状态灯或提示
- 与主机的低时延连接

不负责：

- 复杂上下文理解
- 完整文字注入策略
- 技能编排
- 多模型配置 UI

#### 主机伴随程序层

这是最终产品最关键的一层，建议优先支持 `Windows`。

负责：

- 接收设备音频或触发指令
- 读取当前输入焦点和屏幕上下文
- 管理快捷键、短按、长按、模式切换
- 调本地或云端 `ASR / LLM`
- 执行技能
- 将结果用 Unicode 方式注入当前应用

一句话：

`像闪电说` 的核心差异化，主要不在固件，而在主机伴随程序。

#### AI / 后端层

负责：

- 语音识别
- 文本改写
- 回复生成
- 技能推理
- 个性化记忆

这里可以同时支持：

- 本地模型
- 云端模型
- 第三方模型服务商

### 3. 当前固件仓库应该守住“设备侧边界”

这个仓库当前最适合长期负责的是：

- 设备输入
- 设备音频采集
- 设备与主机通信
- 设备状态与自检
- 一个保底可用的 `BLE HID` fallback

这个仓库当前不适合直接承担的是：

- `Windows` 读屏与上下文理解
- 技能市场或技能运行时
- Unicode 注入适配
- 多模型配置与账号系统

## 推荐架构

### 方案 A：设备采音 + 主机伴随程序处理

这是当前最推荐的方向。

数据流建议是：

1. 用户按下设备语音键
2. 设备开始采集音频
3. 设备通过 `BLE` 自定义通道把音频分片送到 `Windows` 主机伴随程序
4. 主机伴随程序决定走本地 `ASR` 还是云端 `ASR`
5. 主机伴随程序结合屏幕上下文、选中文本、用户技能配置做推理
6. 主机伴随程序把结果以 Unicode 方式注入当前应用

这个方案的优点是：

- 中文输入可行
- 可做上下文理解
- 可做技能执行
- 不要求设备直接联网到云端
- 设备功耗、算力和配置复杂度都更可控

### 方案 B：设备直连云端 + BLE HID 输出

不建议作为最终主方案。

原因是：

- 设备实现复杂度更高
- 中文文本注入依然受限
- 屏幕上下文和技能执行依然缺层

它最多适合作为：

- 设备脱离主机时的简化模式
- 很小范围的 fallback

## 分阶段建议

### 第一阶段：先把设备入口做扎实

目标：

- 语音键控制
- `MIC -> ES8311 -> I2S` 采集
- 本地占位触发
- 稳定日志与自检

对应当前仓库最应该继续推进的是：

- [audio_input_placeholder_plan.md](./audio_input_placeholder_plan.md)
- [voice_key_recording_control_plan.md](./voice_key_recording_control_plan.md)
- [device_logging_selftest_plan.md](./device_logging_selftest_plan.md)

### 第二阶段：把“最终关键层”从 HID 转到主机伴随程序

目标：

- 定义设备与主机伴随程序之间的通信协议
- 明确音频分片上传方式
- 明确主机如何做 Unicode 注入
- 明确主机如何获取上下文和执行技能

这一步是最终做成“像闪电说”的真正分水岭。

### 第三阶段：再决定本地模型与云端模型的组合

目标：

- 本地识别仅做极速转写，还是只做热词 / VAD
- 云端是否负责长文本优化、上下文回复和技能推理
- 用户如何切换模型服务商

### 第四阶段：最后再补产品化细节

包括：

- 隐私策略
- 记忆策略
- 技能配置
- 日志导出
- 更新机制

## 当前建议的实际下一步

如果按“先做成最终可演进架构”来排顺序，当前最合理的下一步不是急着扩 BLE HID 功能，而是先把下面两件事分开：

1. 继续推进当前固件仓库里的设备侧基础能力
2. 单独新建一个主机伴随程序方案或仓库

对当前固件仓库来说，建议的最近顺序是：

1. 完成 `windows_unicode_text_injection_plan`
2. 完成 `audio_input_placeholder_plan`
3. 完成 `audio_input_output_host_capture_plan`
4. 完成 `voice_key_recording_control_plan`
5. 明确设备到主机伴随程序的传输协议草案
6. 再回头看 `backend_text_injection_plan` 是否要升级成“主机 Unicode 注入方案”

其中第 4 点很重要：

当前的 [backend_text_injection_plan.md](./backend_text_injection_plan.md) 更像“后端返回文本后怎么注入”，
但如果目标是“像闪电说”，它最终应该升级成：

- `主机伴随程序文本注入与上下文执行方案`

而不是只停留在设备侧思路。

如果从当前实际排优先级来看：

- “中文输出”这件事很重要
- 但它的正确归属是 `Windows` 主机伴随程序
- 因此当前不建议继续把它当成“固件里的 BLE HID 文本发送增强”
- 当前新的更优先顺序是：
  - 先证明 `主机能把 mock 文本稳定输出到当前输入框`
  - 再证明 `设备能采到音`
  - 后面只需要把识别结果接进现有主机注入链路

## 步骤

### 第一步：确认最终目标采用“三层架构”

状态：`pending`

工作内容：

- 人确认最终目标不是“只有 BLE 键盘”
- 人确认最终目标需要：
  - 设备层
  - 主机伴随程序层
  - AI / 后端层

验收方式：

- 本文档被接受为当前总体方向

人工检查点：

- 人确认后，AI 才能把后续相关计划按这个方向继续细化

### 第二步：明确当前固件仓库只负责设备层

状态：`pending`

工作内容：

- 把当前设备侧能力继续拆解并保持平台边界清晰
- 不把 `Windows` 注入、上下文读取、技能执行硬塞进固件仓库

验收方式：

- 设备侧后续计划仍主要落在 `components/`、`drivers/`、`ports/esp32/`
- 主机侧能力不再被误写成“纯 BLE HID 就能完成”

人工检查点：

- 人确认仓库边界可接受后，AI 再继续细化设备侧计划

### 第三步：单独建立主机伴随程序方案

状态：`pending`

工作内容：

- 新建一个专门的主机侧方案文档或独立仓库
- 设计：
  - 音频接收
  - 屏幕上下文读取
  - Unicode 注入
  - 技能执行

验收方式：

- 存在一份新的主机侧方案文档
- 明确 `Windows` MVP 的技术路线

人工检查点：

- 人确认主机侧路线后，AI 才继续协议和接口设计

## 当前阻塞项

- 还没有独立的主机伴随程序方案
- 当前协议尚未冻结
- 当前最终目标与“仅 BLE 键盘 v1”之间还没有正式拍板优先级

## 备注

一句话总结：

`如果目标只是“会说话的 BLE 键盘”，当前 roadmap 基本够用；如果目标是“像闪电说的嵌入式语音助手”，主机伴随程序才是主战场，固件只是入口层。`
