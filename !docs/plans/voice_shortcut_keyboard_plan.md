# 语音快捷键键盘 A 方案

## 目标

根据当前最新讨论结果，把产品方向收敛成一个更清晰、可分阶段落地的 `A` 方案：

- 硬件本体不是“完整键盘”
- 当前不追求一开始就做跨平台、重型的复杂主机系统
- 当前产品先做成：
  - `4` 个可编程实体键
  - `1` 个旋钮
  - `BLE` 连接
  - 可映射常见快捷键 / 系统键
  - 可触发 `Windows` 主机端语音输入 / agent app
  - 预留键盘麦克风入口

一句话定义：

`当前 v1 先做一个蓝牙语音快捷键键盘 + Windows 轻量语音输入主机端，而不是一开始就做完整跨平台语音助手产品。`

## 讨论后确认的核心结论

基于当前讨论，方向先收敛为 `A`：

1. 语音识别的本质放在电脑端模型侧
2. 当前硬件的作用主要是：
   - 快捷触发
   - 唤醒主机侧语音输入 / agent 能力
   - 提供少量可编程按键
   - 提供旋钮交互
   - 作为麦克风音频入口
3. 当前硬件不是标准全尺寸蓝牙键盘
4. 当前硬件更像：
   - `4` 键 + `1` 旋钮的语音输入快捷控制器
5. 之所以优先选 `A`，是因为：
   - 不希望一开始就要求用户安装一个很重、很复杂、全平台铺开的主机程序
   - 但为了粤语和模型能力，接受先做一个 `Windows` 轻量主机端

## 当前产品定位

当前建议把产品定义为：

`蓝牙语音快捷键键盘 / 蓝牙语音输入控制器 + Windows 轻量主机端`

而不是：

- 完整蓝牙打字键盘
- 先做一个重型复杂、全平台铺开的语音输入法产品
- 当前阶段就覆盖所有平台的复杂伴随程序

## 当前问题

仓库里之前有一些方案默认基于这些前提：

- 先做 `Windows` 主机侧 Unicode 注入
- 先做“后端返回什么字符串，就直接注入什么字符串”
- 先做主机伴随程序

但根据这次讨论，当前主线已经调整为：

- 先做硬件快捷入口
- 先做 `Windows` 轻量语音输入 / agent 主机端
- 先做少量可编程键位
- 先做键盘麦克风入口到主机端的稳定音频链路

因此原先一些“主机 Unicode 注入主线优先”的测试性方案，当前不再适合作为 `v1` 主线。

## 范围

- 明确 `A` 方案的产品边界
- 明确当前硬件应承担的职责
- 明确 `4` 键和旋钮的建议功能边界
- 明确哪些能力当前已具备，哪些还要补
- 重排当前 roadmap

## 不在本次范围内

- 立即实现所有按键自定义 UI
- 立即实现跨平台完整主机伴随程序
- 立即实现自研输入法
- 立即实现智能体 / agent 全能力交互

## 现成方案 / 先例检查

这次优先采用的不是“自造完整语音输入法产品”，而是更接近现成平台能力的组合：

- `BLE HID` 作为标准蓝牙输入设备能力
- `Windows` 轻量语音输入 app
- 流式 ASR + 最终校准
- 系统现有快捷键体系
- 硬件侧做快捷触发、少量可编程输入和麦克风入口

这样做的好处是：

- 比完整跨平台产品更轻
- 平台迁移成本更低
- 硬件价值更清晰
- 更适合先做 `v1`

## 当前建议的功能分层

### 一、硬件必须做的

1. `BLE` 稳定连接
2. `4` 个实体可编程按键
3. `1` 个旋钮输入
4. 按键事件映射到：
   - 常见快捷键
   - 系统键
   - 语音输入触发键
5. 支持基础配置和后续扩展
6. 键盘麦克风音频可稳定送到 `Windows` 主机端

### 二、当前优先做但尽量不复杂化的

1. 在 `Windows` 上先验证一组默认快捷映射
2. 确认主机端语音输入 app 的最小职责
3. 确认键盘端音频到主机端的最小链路
4. 确认旋钮默认行为，例如：
   - 音量
   - 上下切换
   - 滚动
5. 为后续自定义留接口，但当前不强行做完整配置软件

### 三、当前暂不作为主线的

1. 自研跨平台输入法
2. 一开始就做全平台主机程序
3. 一开始就做完整 agent 产品

这些能力不是永远不要，而是：

- 当前先降级为后续增强项
- 不再阻塞 `v1`

## 关于“app”的重新定义

根据当前最新讨论，`app` 不能简单地从主线里删除。

当前更合理的理解是：

- `v1`：先做 `Windows` 轻量语音输入 / agent app
- 后续增强版：再考虑跨平台扩展和更复杂配置能力

所以当前不建议把“完全没有主机 app”作为最终结论。

如果后面真的需要主机程序，它的定位也应当是：

- 配置增强
- agent 增强
- 文本注入增强

而不是：

- 基础可用性的唯一前提

## 关于收音位置的当前判断

当前讨论里实际上分出了两个不同阶段：

### 阶段一：先做键盘收音到 Windows 主机端

当前已经重新确认：

- 键盘麦克风不是摆设
- 设备端收音重新回到主线
- 目标是把声音稳定传到 `Windows` 主机端后端

优先思路改成：

- 先做键盘侧麦克风采集
- 先做设备到 `Windows` 主机端的稳定音频链路
- 主机端负责流式识别和文本输出

### 阶段二：后续再评估键盘麦克风扩展

如果后续要增强，设备端麦克风仍然可以作为：

- 电脑麦克风扩展
- 独立语音入口
- agent 唤醒入口

但这应属于下一阶段，不应继续阻塞当前 `A` 方案。

## 当前需求拆分

### 需求 1：BLE 稳定连接

当前已经具备基础能力，且已完成多轮回连和断链压测。

对应稳定知识：

- [ble_hid_keyboard_input.md](../features/ble_hid_keyboard_input.md)
- [audio_capture_ble_upload.md](../features/audio_capture_ble_upload.md)

### 需求 2：4 个可编程键位

当前应从“完整键盘矩阵”思路，收敛成“少量实体键输入”思路。

重点不是做完整打字键盘，而是：

- 默认键位定义
- 自定义映射边界
- 短按 / 长按 / 组合的可扩展性

### 需求 3：1 个旋钮

当前旋钮更像产品交互增强，不是打字输入本体。

优先考虑默认映射：

- 音量
- 页面滚动
- 候选切换

### 需求 4：触发 Windows 主机端语音输入 / agent app

这是当前 `A` 方案最关键的“语音”部分。

优先目标是：

- 找到 `Windows` 主机端 app 的最合适触发方式
- 把其中一种作为默认键位能力

### 需求 5：键盘麦克风音频上传到主机端

这是当前重新拉回主线的一项。

优先目标是：

- 键盘端采到音频
- 稳定送到 `Windows` 主机端
- 主机端可进入流式识别后端

### 需求 6：少量自定义

当前讨论已经明确有人希望有一定 `DIY` 能力。

因此当前建议是：

- `v1` 就保留“键位可映射”的架构边界
- 但先不做复杂可视化配置系统

## 对旧方案的调整结论

### 当前保留

- `BLE HID` 稳定连接与产品化
- 少量实体键输入
- 语音键触发控制
- 键盘麦克风到主机端的音频链路
- `Windows` 轻量语音输入 / agent app

### 当前降级

- `BLE HID + Windows IME` 中文输出实验主线
- “完全不做主机 app”的假设

这些内容可以保留作历史参考或后续增强候选，但当前不应继续占据 roadmap 第一优先级。

## 新的执行顺序建议

1. 先把 `BLE HID` 稳定性和产品化收完整
2. 先把“少量实体键输入”方案从“完整矩阵”改成“4 键 + 旋钮”方案
3. 先把语音键触发控制方案对齐成“触发 Windows 主机端语音输入 / agent app”
4. 推进设备端音频采集
5. 推进设备到 `Windows` 主机端的流式音频上传
6. 再做主机端最小识别会话

## 当前结论

当前最适合先做的，不是继续围绕“纯快捷键、不做收音”展开，而是：

- 把产品定义成一个蓝牙语音快捷键键盘 + `Windows` 轻量语音输入主机端
- 先做好 `4` 键 + `1` 旋钮
- 先做好快捷键和主机端语音输入触发
- 先把键盘音频稳定传到主机端

这更符合当前讨论结论，也更适合作为 `v1`。
