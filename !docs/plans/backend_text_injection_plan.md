# 返回文本注入方案

> 状态说明：这份方案保留作占位参考，但当前方向需要升级。
>
> 如果目标是稳定中文输入和“类似闪电说”的体验，这件事应主要由 `Windows` 主机伴随程序承担，而不是继续假设“纯 BLE HID 直接完成 Unicode 中文注入”。
>
> 当前更推荐直接参考：
> [windows_unicode_text_injection_plan.md](./windows_unicode_text_injection_plan.md)

## 目标

在音频上传之后，把后端返回的文本结果稳定注入到 Windows 主机输入框中，形成语音输入闭环。

## 问题

当前仓库已经有 BLE HID 键盘输出链路，但还没有：

- 文本结果下行通道
- 文本结果缓冲与提交策略
- 与 HID 输出的对接规则
- 失败回退与重复注入防护

## 范围

- 下行文本返回架构选择
- 文本提交策略
- 与现有 HID 输出链路的对接
- 失败、重复与取消处理

## 不在本次范围内

- 云端识别实现
- 复杂输入法联动
- 富文本输出

## 前提与依赖

- 依赖后端或中转端的下行设计
- 依赖已完成的 BLE HID 输出链路
- 依赖上传链路和语音键状态机

## 步骤

### 第一步：确认文本下行架构

状态：`pending`

工作内容：

- 确认文本结果通过什么路径回到设备
- 明确这条路径与 HID 输出链路如何协同

验收方式：

- 文档中明确写出下行架构结论

人工检查点：

- 人确认下行架构后，AI 才进入第二步

### 第二步：定义文本注入策略

状态：`pending`

工作内容：

- 明确何时提交文本
- 明确部分结果和最终结果是否区分
- 明确取消、重试和去重逻辑

验收方式：

- 文档中明确写出文本注入策略

人工检查点：

- 人确认文本注入策略可接受后，AI 才进入第三步

### 第三步：定义端到端验证方式

状态：`pending`

工作内容：

- 明确如何验证“返回文本 -> HID 输出 -> Windows 收到文本”

验收方式：

- 文档中明确写出验证方式和成功标志

人工检查点：

- 人确认返回文本注入方案可接受后，AI 才进入实现

## 当前阻塞项

- 依赖下行架构和后端接口冻结
- 依赖单独的 `Windows` 主机伴随程序方案
- 当前仍缺少正式的 Unicode 中文注入路线定义

## 备注

- 当前最小占位链路可以先用固定测试字符串
- 正式产品链路要在这里替换为真实返回文本
- 如果后续新建专门的 `Windows` 主机侧中文注入方案，并且内容稳定，这份旧方案应删除或并入新方案
