# BLE 键盘产品化方案

## 目标

把当前已经能工作的 BLE HID 键盘 demo，推进到“更像产品能力而不是单纯验证链路”的状态。

## 问题

当前 BLE HID 链路已经完成了字符注入验证，但仍然偏 seed 工程：

- 配对、绑定、重连策略还没有产品化定义
- 电量上报还没有纳入
- 主机输出状态处理还没有产品化
- 缺少对连接体验的统一验收标准
- 缺少对“断链后是否自动恢复”的明确稳定性目标
- 缺少持续可复用的蓝牙连接测试脚本约束

## 范围

- BLE 设备命名与身份信息
- 配对、绑定、重连行为
- 电量上报
- 主机输出状态处理，例如键盘 LED/控制事件
- 连接状态日志与基本诊断
- 蓝牙连接稳定性目标
- 蓝牙断链 / 假连接态 / reset 后回连的脚本化验证

## 不在本次范围内

- `2.4G dongle`
- Wi‑Fi 传输
- 复杂低功耗策略
- 完整量产认证流程

## 前提与依赖

- 当前 BLE HID 基础验证链路已完成
- 当前开发板具备电池电量检测相关硬件预留
- 当前仍以 `ESP32-S3` 平台 bring-up 为主
- 当前 BLE HID 稳定总结位于：
  [ble_hid_keyboard_input.md](../features/ble_hid_keyboard_input.md)

## 当前建议的稳定性目标

`v1` 阶段至少应明确收掉以下蓝牙连接稳定性目标：

1. reset 后自动回连
2. 设备空闲一段时间后再次唤醒仍能回连
3. 主机蓝牙服务短暂异常后可恢复
4. Windows UI 显示“已连接”但 HID 实际未恢复时，有明确检测与恢复路径
5. 所有关键场景都能通过脚本复测，而不是只靠人工点击界面

## 当前建议保留的测试脚本能力

后续不要求继续保留之前那两份历史压测脚本原样，但产品化阶段必须重新具备以下脚本能力：

- `capture_serial.ps1`
  用于抓 reset 后回连日志
- `verify_ble_hid.ps1`
  用于检查固件侧连接与 HID 发送结果
- `verify_ble_hid_end_to_end.ps1`
  用于检查主机侧是否真的收到输入
- 一个新的稳定性回归脚本
  - 覆盖多轮 `reset -> 自动回连 -> 发字`
  - 覆盖空闲后再回连
- 一个新的异常恢复脚本
  - 覆盖主机蓝牙服务重启或假连接态恢复

脚本名字后续可以调整，但这几类能力必须保留。

## 步骤

### 第一步：确认 BLE 产品化最小能力边界

状态：`pending`

工作内容：

- 明确 `v1` 必须收掉的 BLE 产品化能力
- 在“必须项”和“可延后项”之间做切分

验收方式：

- 文档中明确列出 `v1` 必须项与可延后项

人工检查点：

- 人确认 `v1` BLE 产品化边界后，AI 才进入第二步

### 第二步：固化连接与身份策略

状态：`pending`

工作内容：

- 明确设备命名、配对、绑定、重连和连接状态机
- 明确 reset 后回连、空闲恢复、异常恢复的目标行为

验收方式：

- 文档中明确写出连接策略与验收行为
- 文档中明确写出稳定性目标与失败判定条件

人工检查点：

- 人确认连接策略可接受后，AI 才进入第三步

### 第三步：固化稳定性测试脚本与回归标准

状态：`pending`

工作内容：

- 明确产品化阶段必须保留哪些蓝牙回归脚本
- 明确每类脚本覆盖的断链 / 恢复场景
- 明确哪些场景属于每次改动后都要回归

验收方式：

- 文档中明确列出脚本职责
- 文档中明确列出回归场景表

人工检查点：

- 人确认测试脚本范围可接受后，AI 才进入第四步

### 第四步：补齐电量与主机状态处理方案

状态：`pending`

工作内容：

- 明确电量上报方式
- 明确主机输出状态如何处理和记录

验收方式：

- 文档中明确写出电量上报和主机状态处理方案

人工检查点：

- 人确认产品化范围完整后，AI 才进入实现

## 当前阻塞项

- 需要先明确 `v1` 的 BLE 产品化边界
- 需要把“稳定性目标”和“测试脚本”从历史经验正式升级为当前 plan 里的显式内容

## 备注

- 该方案主要收的是“连接体验和产品行为”
- 不替代已完成的 BLE HID 输入验证文档
- 但后续所有音频上传与语音主线，都默认依赖这里定义好的 BLE 稳定性与回归标准
